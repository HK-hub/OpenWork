## 0. 转向背景

旧基线（统一设计契约 v4.3）定位为「Electron Desktop 单机应用 + headless 多客户端引擎」，技术底座为 SQLite + 自研 JSON-RPC 多 Transport + Worker Threads。

需求变化后不再成立的前提：

1. 客户端暂时不需要 Electron 与 CLI，只需 Web UI；
2. 数据库由 SQLite 更换为 PostgreSQL；
3. 后端要求类 Spring Boot 的 IoC/DI 体验、强制面向接口编程（DIP）、DDD/CQRS/Clean 分层；
4. 旧功能规划范围过大且部分能力定义含糊，需要重裁。

由此形成以下 16 项决策。

## 2. 决策详录

### D-01 部署模式：本机单用户 Web 应用

- **背景**: 去 Electron 后必须重新回答「服务跑在哪、谁在用」。候选：A 本机单用户 / B 团队自托管 / C 公有云 SaaS。
- **决策**: 选 A。NestJS 后端运行于开发者本机，浏览器访问 `http://localhost:<port>`；PostgreSQL 以本地实例（Docker Compose 提供）运行。
- **理由**: 最贴近原 Desktop 形态，改动最小；保住「本地优先/数据主权」定位；为未来升级团队自托管（B）预留架构空间。
- **后果**: 无多租户；不做计费/配额；局域网访问默认关闭（见 D-03）。

### D-02 工作区访问模型：本机目录直读

- **背景**: Coding Agent 必须读写代码。候选：A 本机直读 / B Docker 沙箱 / C 托管工作区 + Git 同步。
- **决策**: 选 A。用户在 Web UI 注册本机项目路径（可多个），后端经文件系统网关直接读写；安全边界 = L0-L3 权限网关 + 注册路径白名单。
- **理由**: Windows 下避免 Docker Desktop 常驻开销与 IO 性能损失；体验最接近 IDE 类产品。
- **后果**: 不引入容器生命周期管理；沙箱隔离强度依赖权限网关而非 OS 级隔离（已知取舍）。

### D-03 认证体系：种子单用户 + 可选 Token

- **决策**: PG 从第一天存在 `users` 表（含一个种子默认用户）；所有业务表带可空 `owner_id` 外键；后端默认只绑定 `127.0.0.1`；提供可选 Bearer Token 开关用于局域网访问。
- **理由**: schema 提前容纳用户维度，未来升级多用户时表结构基本不动，只增加注册/OAuth 流程；避免后期痛苦迁移。
- **后果**: v0.1 不实现注册/登录 UI/RBAC。

### D-04 v0.1 功能范围：极简内核

- **背景**: 旧 v0.1 已是收缩版（4 模块 12 表），换底座后仍偏大，且部分能力（五子循环、动态结果调整全量形态等）定义含糊。
- **决策**: v0.1 = 会话/流式对话 + 单层主循环 + 核心工具集 + 权限确认 + Provider 抽象 + PG 持久化 + 基础可观测。MCP、RAG、记忆、Hooks/Skills/Plugins、Sub-Agent、SCHED、GOAL、PROMPT 库、Profile 全部延后。
- **理由**: 最快跑通「可用」闭环；被砍能力在旧文档中本就语义不清，先延后再精确定义。

### D-05 Agent 循环形态：单层主循环

- **决策**: 组装上下文 → 调 LLM → 执行工具 → 结果回灌 → 直至无工具调用或触发终止条件（最大步数/预算/用户中止）。工具失败将错误作为 Observation 回给 LLM 自行纠错。Planning/Verification/Reflection/Recovery 子循环延后至 v0.2+ 再精确定义。
- **理由**: 子循环的触发条件/交互语义在旧文档中未定义清楚，贸然实现必然产出半成品。

### D-06 可干预性：基础干预三件套

- **决策**: v0.1 仅实现 ①停止按钮 ②从任意历史消息编辑并重跑（本质为 fork 分支）③L2+ 危险工具调用前的确认/拒绝弹窗。工具结果修改、决策干预、上下文注入等高阶形态延后。
- **理由**: 三件套覆盖日常干预诉求，且消息已在 PG 中树形存储，fork 成本低；高阶形态需要 Loop 状态机支持中途改写已序列化执行记录，复杂度高。

### D-07 内置工具集：10 个核心工具

- **决策**: `read_file / write_file / edit_file / delete_file / move_file / glob / grep / run_command / web_fetch / todo_write`。
- **理由**: 文件增删改查闭环（缺 delete/move 会导致重构任务卡死），todo_write 成本低 UX 价值高。语义搜索/LSP/浏览器/Sub-Agent 等延后。

### D-08 可观测深度：全落库 + 轻展示

- **决策**: loop_steps / tool_calls / model_calls 全量持久化（审计必需）；UI 提供消息流内工具调用卡片 + 会话级 token/费用汇总。Trace 时间线、Prompt Inspector、上下文来源树、断点调试器延后。

### D-09 后端框架/IoC：NestJS

- **背景**: 需求要求类 Spring Boot 的 DI/IoC。事实澄清：TS 生态最接近的是 **NestJS**（借鉴 Angular，框架无关，非 Vue/React 生态）。备选 InversifyJS/tsyringe/Awilix 为纯 IoC 容器；Foal/Midway 社区较小。
- **决策**: NestJS 11 作为唯一组装根。所有 Repository/工具/Provider Adapter 注册为 Provider，经接口 token 注入，天然满足 DIP。
- **代价**: 装饰器 + 反射元数据学习成本（接受）。

### D-10 CQRS 深度：轻量 CQRS

- **决策**: 使用 `@nestjs/cqrs` 的 CommandBus/QueryBus 分离读写路径；写路径走聚合 + Repository 接口，读路径用面向列表/统计的查询服务；不引入 EventBus 持久化事件存储/事件溯源。Agent 运行时流式事件走 WebSocket 通道，与 CQRS 事件无关。

### D-11 ORM：Drizzle

- **决策**: Drizzle ORM（TS 编写 schema、全链路类型推断、接近原生 SQL、drizzle-kit 迁移、官方 pgvector 支持）。Repository 接口在领域层，Drizzle 实现封在基础设施层。
- **否决**: Prisma（独立查询引擎二进制、复杂 SQL 能力弱）；TypeORM（类型安全弱、实体易泄漏进领域层）。

### D-12 API 契约：REST + WebSocket 全双工

- **决策**: 常规 CRUD 走 REST（Nest 控制器 + Swagger 自动文档）；流式交互、数据推送、消息输入、事件处理、PTY 流、文件流走 **WebSocket 全双工通道**（支持二进制帧与自定义序列化协议）。
- **补充**: monorepo 内建 `packages/contracts` 共享枚举/类型/Zod schema，作为前后端唯一事实源。

### D-13 前端载体：Vite SPA

- **决策**: Vite SPA + React 19 + antd v5 + Tailwind v4 + Zustand/TanStack Query + Monaco（Diff 视图）。dev 时 proxy 到 NestJS，生产可由后端静态托管。
- **否决**: Next.js（本机工具无 SSR/SEO 收益）；Vue/Nuxt（与既有生态断裂）。

### D-14 交互式命令：PTY + 人工接管

- **背景**: 用户实测痛点——Agent 执行 shell 命令遇到 yes/密码提示会永久 hang。
- **决策**: 所有 `run_command` 默认跑在 node-pty（Windows 用 ConPTY）中；默认注入非交互环境变量（`CI=true` 等）+ 全局超时兜底；UI 命令卡片内置「发送输入」能力（复用 WS 双工通道），检测到疑似等待输入或用户主动时接管输入。
- **理由**: 纯非交互方案对 `sudo` 这类直接读 `/dev/tty` 的命令无解；PTY 是根治方案。代价：node-pty 原生依赖 + ANSI 转义清洗。

### D-15 工程杂项

- 对话输入框：轻量受控 textarea（TipTap 富文本延后）
- 包管理器：npm workspaces + Turborepo（延续旧契约）
- 配置与密钥：业务配置入 PG（configs/config_history），API Key 加密入库（本机密钥文件派生加密钥），`DATABASE_URL` 等基础设施连接串走环境变量
- Monorepo 结构：`apps/web` + `apps/server` + `packages/contracts` 三包；分层在 server 内部完成
