# OpenWork 功能批判报告

> **从 Claude Code / OpenCode 竞品视角，对 OpenWork 当前实现的毁灭性批判**

---

## 〇、总体评价

OpenWork 宣称对标 Claude Code、OpenCode、Codex CLI，但当前实现是 **一具空壳**。80% 的代码是接口声明、类型定义和空方法体。核心子系统（subagent、background task、agent team）**完全不可用**。这是一个连 MVP 都算不上的原型玩具，却包装成 "生产级" "商用级" 产品。以下逐项揭露。

---

## 一、SubAgent 系统 —— 只会想，不会做

### 声称：对标 Claude Code Subagents / OpenCode Task 工具

### 现实：一个只能产生文本的 LLM 循环，无法调用任何工具

**致命缺陷 #1：工具调用循环完全缺失**

文件 `subagent-manager.ts` 第 146 行，`buildToolDefs()` 向 LLM 发送了 11 个工具定义（read_file, write_file, grep 等）。但当 LLM 响应中包含 `tool_calls` 时，第 143 行的代码：

```typescript
const response = await adapter.chat({ ...tools: buildToolDefs(...) });
// ...
const text = response.text || '';
```

**只读取了 `response.text`，完全忽略了 `response.toolCalls`。** subagent 可以"看到"工具列表，可以要求调用 `read_file`，但这个请求会被直接丢弃。subagent 是一个"只能思考、不能行动"的幽灵——它对代码提建议，但永远无法读取、搜索或修改任何文件。

Claude Code 的 SubAgent 可以执行完整的工具链：Bash → Read → Edit → Write → Bash 测试 → 返回结果。OpenWork 的 SubAgent：一个死循环文本生成器。

**致命缺陷 #2：`task_spawn` 工具是 no-op**

文件 `extra-tools.ts` TaskSpawnTool（约第 406-428 行）：

```typescript
const result = await this.services.subAgentManager.spawn({ ... });
return { output: `Sub-agent spawned: ${result.id}\nStatus: ${result.status}` };
```

它调用了 `spawn()` ——**仅此而已**。它从未调用 `execute()`。当 Agent 在对话中使用 `task_spawn` 工具时：
1. 一个 `SubAgentInstance` 被创建，状态为 `'pending'`
2. 工具返回 `"Status: pending"` 
3. 主 Agent 以为 subagent 正在工作
4. **没有任何东西实际执行**。没有 LLM 调用，没有工作完成。实例成为僵尸，永远留在内存中。

对比 OpenCode 的 `task` 工具：它会真正创建子会话，运行子 Agent 的 prompt，返回结构化结果 `{ output, taskId, state }`。

**致命缺陷 #3：三种模式是死标签**

`master_slave`、`parallel`、`expert` 三种协作模式被接受、存储，但在所有执行路径中被完全忽略。`executeParallel()` 只是 N 个独立 `execute()` 的并发运行器。没有任何：
- 跨 Agent 通信
- 共享内存/黑板
- 结果合并
- 依赖图管理
- Master Agent 审查子 Agent 结果

## 二、Background Task 系统 —— 名字叫"后台"，实际既不后台也不任务

### 声称：对标 Claude Code Background Agents / OpenCode Background Jobs

### 现实：一个硬编码的单例代理转发器

**致命缺陷 #4：硬编码 agent 名**

文件 `background-agent-service.ts` 第 108-110 行：

```typescript
const agentName = `bg-${job.id.slice(0, 8)}`;  // 定义了但不用！
const subAgent = await this.subAgentManager.spawn({
    agentName: 'code-reviewer',  // ← 硬编码！
```

无论用户请求什么模式（build/plan/test/fix/review），后台任务永远创建一个 **code-reviewer**。如果用户想运行 test-writer，他们会得到一个 code-reviewer。如果用户想运行 debugger，他们会得到一个 code-reviewer。`agentName` 变量在第 108 行计算出来，但第 110 行被硬编码覆盖。

**致命缺陷 #5：进度条是假的**

第 124 行：
```typescript
job.progress = Math.min(90, 10 + Math.floor(80 * (0.1)));  // = 永远 18
```

无论 subagent 执行到哪一步，进度永远是 **18%**。没有真实的状态更新，没有步骤计数反馈。

**致命缺陷 #6：不是真正的后台执行**

尽管名字叫 "BackgroundAgentService"，所有任务都在主进程的事件循环上运行。没有 worker threads，没有子进程，没有隔离的 Node.js 运行时。一个长时间运行的任务会阻塞其他所有 Node.js 工作。

对比 Claude Code 的 Background Agents：真实的子进程隔离，通过 task output file 通信，可在 Agent View 中监控。

---

## 三、Agent Team 系统 —— 完全不存在

### 声称：对标 Claude Code Agent Teams

### 现实：零行代码

OpenWork 没有任何 Agent Team 相关实现。没有一个文件、一个类、一个接口涉及到：
- 多 Agent 协调
- 任务分配与认领
- Agent 间消息传递
- 团队配置
- TeammateIdle / TaskCreated / TaskCompleted 事件

`SubAgentManager` 的三个模式标签暗示了团队意图，但连最基本的"Master 审查 SubAgent 结果"逻辑都不存在。

## 六、结论

OpenWork 当前是一个 **界面声明型项目**——大量接口、类型、方法签名看起来完整，但核心执行路径要么缺失，要么是硬编码死逻辑。它在 README 和设计文档中声称对标 Claude Code，但任何实际的端到端测试都会暴露这些系统完全无法工作。

**开发者不应该声称"功能已达标"，直到这些系统通过了实际的端到端测试。**
