## 2. 核心架构方案（三种方案对比）

### 2.1 方案 A：纯 TypeScript Monolith

```
┌──────────────────────────────────────────────┐
│                  Electron Main Process        │
│  ┌────────────────────────────────────────┐  │
│  │         Agent Engine (TS)               │  │
│  │  ┌──────┐ ┌──────┐ ┌──────┐ ┌───────┐ │  │
│  │  │ Loop │ │Tool  │ │MCP   │ │Prompt │ │  │
│  │  │Engine│ │System│ │Client│ │Engine │ │  │
│  │  └──────┘ └──────┘ └──────┘ └───────┘ │  │
│  │  ┌──────┐ ┌──────┐ ┌──────┐           │  │
│  │  │Context│ │Perm  │ │Config│           │  │
│  │  │Engine│ │Gateway│ │System│           │  │
│  │  └──────┘ └──────┘ └──────┘           │  │
│  └────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────┐  │
│  │         SQLite (better-sqlite3)         │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
         ↕ IPC (contextBridge)
┌──────────────────────────────────────────────┐
│              Electron Renderer Process        │
│  ┌────────────────────────────────────────┐  │
│  │   React 19 + Vite + @lobehub/ui (主) + antd (兜底) │
│  │  ┌────────┐ ┌────────┐ ┌────────────┐ │  │
│  │  │ Chat   │ │ Loop   │ │ Settings   │ │  │
│  │  │ Panel  │ │ Trace  │ │ Panel      │ │  │
│  │  └────────┘ └────────┘ └────────────┘ │  │
│  └────────────────────────────────────────┘  │
```

**优点**：单一语言、调试简单、部署简单
**缺点**：主进程阻塞影响 UI、Agent 崩溃 = 整个应用崩溃、无法多核并行

**适用场景**：MVP 快速验证，小团队

**适用场景**：v1.0+ 企业版，团队协作

### 2.5 推荐方案

> **🏆 推荐方案 B：主进程 + Worker Threads**
>
> **MVP 阶段 (v0.1-v0.2)**: 方案 B，快速验证核心 Agent 能力
> **成长阶段 (v0.3-v0.9)**: 方案 B 优化，逐步抽取独立服务
> **企业版 (v1.0+)**: 迁移到方案 C，支持团队协作和远程部署
>
> **迁移路径**：方案 B 的 Worker 接口设计时预留 HTTP 适配层，可平滑迁移到方案 C

## 3. 前端技术选型

### 3.1 核心框架

| 维度             | React 19 | Vue 3.5 | Svelte 5 | SolidJS |
| -------------- | :------: | :-----: | :------: | :-----: |
| **最新稳定版**      |  19.1.0  |  3.5.x  |    5.x   |  1.9.x  |
| **生态规模**       |   ⭐⭐⭐⭐⭐  |   ⭐⭐⭐⭐  |    ⭐⭐⭐   |    ⭐⭐   |
| **TypeScript** |   ⭐⭐⭐⭐⭐  |   ⭐⭐⭐⭐  |    ⭐⭐⭐   |  ⭐⭐⭐⭐⭐  |
| **UI 库兼容**     |    最广    |    中等   |    有限    |    有限   |
| **社区贡献**       |    最大    |  大（中国强） |     中    |    小    |

> **选择: React 19 + TypeScript 5.7**
>
> 理由：生态最广、antd v6 原生支持 React 19、社区贡献者最多、@lobehub/ui 全家桶原生支持

### 3.2 UI 框架与组件库（LobeHub 生态全面集成）

> **关键决策**：全面采用 LobeHub 生态替换原 shadcn/ui 方案，并 **新增 @lobehub/editor 作为 AI 交互输入编辑器**。**禁止 antd v6 作为首选 UI 框架**，antd v6 + antd-style 仅作为 @lobehub/ui 底层依赖存在，不直接使用其原生 API。
> 详见：[09-LobeHub生态集成方案.md v1.3 §0.4](./09-LobeHub生态集成方案.md)

| 组件库                 | 版本      | 定位                                    | 选择理由                                                 |

> **设计决策 D3.1**: 代码编辑与 AI 对话输入采用 **双编辑器架构**，各司其职。

| 编辑器          | 用途                   | 选型                                       | 理由                               |
| ------------ | -------------------- | ---------------------------------------- | -------------------------------- |
| **代码编辑器**    | 右侧资源管理器/文件预览/Diff 查看 | **Monaco Editor** (@monaco-editor/react) | IDE 级能力、语法高亮、多光标、LSP 集成          |

- @lobehub/editor 基于 Lexical，可深度定制节点类型，完美适配「指令式 AI 输入」交互

### 4.3 Agent Loop 设计参考

> **重要：直接参考 OpenCode 的 Agent Loop 设计**
>
> OpenCode 的核心 Agentic Loop 设计非常优秀，我们应直接参考其架构：
>
> ```
> SessionPrompt.loop() {
>   while (finish === "tool-calls") {
>     1. 解析可用工具（按 Agent + Model 筛选）
>     2. 注入系统提醒
>     3. LLM.stream() 流式调用
>     4. 处理流事件（text-delta / reasoning-delta / tool-call）
>     5. 检查完成条件 → 无工具调用则结束
>   }
> }
> ```
>
> **我们可复用的设计模式**：
>
> - Tool 的 lazy 初始化模式（`Tool.Info<Params>`）
> - 模型感知的工具筛选（GPT → apply\_patch, Claude → edit）
> - 9 层容错编辑匹配策略
> - Doom Loop 检测（连续 3 次相同调用触发警告）
> - 消息压缩（Compaction Agent）

### 4.4 关键设计决策

| 决策         | 方案                  | 理由                              |
| ---------- | ------------------- | ------------------------------- |
| Agent Loop | 单循环 + 子循环           | 参考 OpenCode，复杂任务用 task 工具委派     |
| 工具执行       | Worker Thread 隔离    | 崩溃不影响主循环                        |
| 模型抽象       | Provider Adapter 模式 | 支持 Anthropic/OpenAI/Ollama/兼容接口 |
| 提示词管理      | 七层洋葱模型              | 继承原设计文档                         |
| 权限控制       | 规则引擎                | 参考 OpenCode 的分层规则 + BashArity   |

## 9. 项目初始化方案

### 9.1 目录结构

> **架构原则**（v3.5 调整）：项目实施**前后端分离**。虽然全部使用 TypeScript，但工程上明确拆分为：
>
> - **前端（apps/\*）**：app / tui / web 页面，属于 thin clients，不包含任何 Agent 核心流程与数据库操作。
> - **后端（packages/\*）**：Agent 核心流程、数据库操作、能力扩展层、模型抽象层等，作为 headless 引擎独立存在。
> - **通信**：前端通过 JSON-RPC 2.0 协议经多种 Transport（HTTP/SSE · WebSocket · stdio · Electron IPC · Embedded）调用后端。

#### 9.1.1 后端运行模式（三种）

后端 `@opencode/server` 支持三种运行模式，前端通过 Transport 客户端透明接入：

| 模式                    | 描述                                         | 适用场景               | Transport                  |
| --------------------- | ------------------------------------------ | ------------------ | -------------------------- |
| **嵌入式 (Embedded)**    | 后端直接以前进程序加载到宿主进程（如 Electron Main），零 IPC 开销 | Desktop 默认         | `embedded.ts`              |
| **服务式 (Service)**     | 后端作为独立 Node.js 进程运行，监听 HTTP/WS 端口          | Web 应用、远程访问、多客户端共享 | `http.ts` + `websocket.ts` |
| **子进程式 (Subprocess)** | 后端作为子进程启动，通过 stdio 通信                      | CLI / TUI          | `stdio.ts`                 |

#### 9.1.2 前后端边界约束

| 约束             | 前端 (apps/\*)     | 后端 (packages/core + packages/server) |
| -------------- | ---------------- | ------------------------------------ |
| Agent Loop 引擎  | ❌ 禁止             | ✅ 独占                                 |
| 数据库操作          | ❌ 禁止             | ✅ 独占                                 |
| 工具执行           | ❌ 禁止             | ✅ 独占                                 |
| 模型调用           | ❌ 禁止             | ✅ 独占                                 |

### 9.3 热重载矩阵（Monorepo 开发体验）

> **背景**（v3.6 新增，对应 [07 报告](./07-多角色审视评估报告.md) M16 / §6.4）：Monorepo 多包结构下，各包/应用的变更场景与热重载方式不一致，开发者需明确知道修改哪个包后如何生效，避免在 5 种 Transport 实现中分别 `console.log` 调试。

| 包/应用 | 变更场景 | 热重载方式 | 重启边界 | 已知限制 |
|---------|----------|------------|----------|----------|
| apps/desktop (renderer) | React 组件 / 样式 / 布局变更 | Vite HMR（毫秒级，保留组件状态） | 无需重启 | — |
| apps/desktop (main) | Electron Main 进程逻辑变更 | electron-vite 自动重启 Electron 主进程 | 主进程重启，渲染进程状态丢失 | — |
| apps/desktop (preload) | contextBridge 脚手架变更 | 需手动重启 electron-vite | 主进程 + 渲染进程均重启 | — |
| packages/core | Agent 引擎 / 工具 / 权限等核心逻辑变更 | `tsc --watch` 增量编译 + Desktop 主进程重启 | 需重启 Desktop（嵌入式模式重新加载 @opencode/core） | better-sqlite3 / sqlite-vec / isolated-vm 等 native 模块变更需全量重新构建 |
| packages/api | JSON-RPC 方法签名 / 事件类型变更 | `tsc --watch` + 全量类型检查 | 类型变更影响所有依赖包，需重启 Desktop | 不含运行时逻辑，仅类型层 |
| packages/server | Transport 实现 / 中间件 / 路由变更 | nodemon 监听重启（服务式模式） | 后端进程重启，客户端需重连 | 嵌入式模式下 packages/server 变更等同 packages/core 重启 |
| packages/transport-* | Transport 客户端实现变更 | `tsc --watch` + 前端 HMR | 仅影响对应客户端 | — |
| apps/tui / apps/cli | TUI/CLI 逻辑变更 | 手动重新运行（Ink / Commander 无 HMR） | 进程重启 | v0.2+ 才实现 |

**已知限制与注意事项**：

1. **native 模块变更需全量重启**：better-sqlite3、sqlite-vec、isolated-vm、web-tree-sitter 任一变更或版本升级，需执行 `npm run build` 全量重建，并重启 Electron（含 `electron-rebuild`），无法热重载。
2. **packages/core 变更影响嵌入式模式**：嵌入式模式下 Desktop 直接 `import @opencode/core`，core 的任何变更需重启 Desktop 主进程才能生效（无 HMR）；Turborepo `dev` 任务通过 `tsc --watch` 增量编译 + npm workspaces 符号链接即时同步产物。
3. **Turborepo dev 任务编排**：`turbo run dev` 会并行启动 apps/desktop 的 electron-vite dev 与 packages/core 的 `tsc --watch`，core 增量产物通过 npm workspaces 符号链接即时同步。
4. **Worker Threads 不支持 HMR**：Agent Worker / Tool Worker / Indexer Worker 代码变更后，需重启后端进程以重新创建 Worker，无法热替换。
5. **stdio/HTTP/WebSocket Transport 调试**：跨 Transport 的 JSON-RPC 调试需借助 `debug.rpc.trace` 事件（见 [06-详细设计文档](./06-详细设计文档.md) §4），统一在所有 Transport 实现中发布。

## 11. 回退与降级方案

> **背景**（v3.6 新增，对应 [07 报告](./07-多角色审视评估报告.md) M9 / §4.3）：v4.1 前后端分离架构相对 v4.0 单体增加 30-50% 后端开发量（L3 API 契约 + L4 Transport 层 + OpenCodeClient SDK + JSON-RPC 封装 + 序列化）。若 v0.1 中期发现某项决策无法按期交付或性能不达标，需有明确的 Plan B，避免团队陷入无回退路径的困境。

### 11.1 回退 1：JSON-RPC 性能不达标 → Desktop 直连 core

| 维度 | 说明 |
|------|------|
| **触发条件** | 嵌入式模式下 JSON-RPC 序列化/反序列化开销导致单次工具调用端到端延迟 P99 > 500ms，或流式响应卡顿可感知 |
| **回退方案** | v0.1 允许 Desktop Main 进程直接 `import { createBackend } from '@opencode/core'`，绕过 Transport 层（L4）与 @opencode/server 路由，保留 @opencode/api 类型契约约束但不强制物理分离 |
| **影响范围** | 仅影响 Desktop 嵌入式模式；@opencode/api 契约层保留，后续切换回 Transport 层无需改前端类型；服务式模式（v0.2+）不受影响，仍走完整 Transport 链路 |
| **决策点** | Phase 2（Agent 引擎）末期进行性能基准测试，若不达标则在 Phase 3 前决策回退 |

### 11.2 回退 2：isolated-vm 编译失败 → worker_threads

| 维度 | 说明 |
|------|------|
| **触发条件** | isolated-vm 在 Electron 35 / Node.js 22 双环境下编译失败（V8 版本不匹配），或 `electron-rebuild` 无法产出可用二进制 |
| **回退方案** | 插件沙箱降级为 `worker_threads`（Node.js 内置，无 native 编译依赖），通过进程间消息传递实现隔离；权限粒度从 V8 Isolate 级降为 Worker 级 |
| **影响范围** | 仅影响 Plugin 系统（v0.2+）；沙箱隔离强度略降（Worker 仍可访问 Node API，需配合权限白名单）；性能略降但可接受 |
| **决策点** | v0.2 Phase 6（Plugin 系统）启动时验证编译，若失败则降级 |

### 11.3 回退 3：sqlite-vec 性能不足 → 纯 FTS5 + 手动过滤

| 维度 | 说明 |
|------|------|
| **触发条件** | sqlite-vec 向量检索在 100w chunks 规模下 P99 > 200ms，或 SQLite 扩展加载不稳定 |
| **回退方案** | 向量检索降级为纯 FTS5 全文检索 + 关键词手动过滤；语义检索能力延后（待 v0.3+ 引入外部 embedding 服务） |
| **影响范围** | 影响 Memory 高级特性（v0.3）与代码库语义检索；FTS5 关键词检索仍可用，仅丢失语义相似度 |
| **决策点** | v0.3 Phase 8（Memory 高级特性）前进行基准测试 |

### 11.4 回退 4：Turborepo 增量构建不稳定 → npm workspaces + tsc --build

| 维度 | 说明 |
|------|------|
| **触发条件** | Turborepo 2.x 增量缓存命中率低导致 dev 任务频繁全量重建，或 `turbo run dev` 在 Electron 项目中出现任务编排异常 |
| **回退方案** | 降级为纯 `npm workspaces` + `tsc --build`（TypeScript Project References 原生增量构建）；移除 turbo.json，根 package.json scripts 改为直接调用各包 |
| **影响范围** | 影响全包构建速度（增量构建仍可用 tsc --build，但失去 Turborepo 远程缓存与任务并行编排）；不影响功能正确性 |
| **决策点** | Phase 0（项目初始化）末期验证，若不稳定则立即降级 |

### 11.5 回退决策流程

1. **监测**：每个 Phase 末期进行性能基准测试与编译验证；
2. **评估**：由技术负责人评估回退的触发条件是否满足；
3. **决策**：回退决策记录到 `docs/design/decisions/` 并同步更新本节；
4. **回滚**：回退实施后，原方案保留在分支中，待条件成熟可重新启用。

3. **预警提示**: 上下文超过 90% 时进度条变红，提示用户压缩或新建会话

#### 12.4.4 交互联动

- 进度条颜色规则：< 70% 绿色 / < 90% 橙色 / ≥ 90% 红色
- 点击进度条 → 展开上下文来源详情浮层（文件/会话/检索/工具调用各占多少）
- 点击模型切换器 → 下拉显示所有已配置 Provider 的模型列表，含品牌图标与状态点
- 切换模型 → 调用 `config.setModel(provider, model)` → 上下文窗口预算重算 → 进度条刷新
- 点击权限模式 → 下拉显示四级模式，切换后影响后续所有工具调用审批行为

- ESC → 清空编辑器 / 取消正在输入的命令

### 12.10 主题与四色同步

基于 [09-LobeHub生态集成方案.md 附录 B](./09-LobeHub生态集成方案.md)，实现 UI / Monaco / LobeEditor / 终端四色同步。

> **关键决策**：UI 层主题通过 `@lobehub/ui` ThemeProvider 注入，**禁止**直接调用 `antd-style` `createTheme` API。

```typescript
// 通过 @lobehub/ui ThemeProvider 注入主题 (推荐方式)
import { ThemeProvider } from '@lobehub/ui';

<App>
  <ThemeProvider themeMode="dark" customToken={{ /* 自定义 token */ }}>
    {/* 子组件 */}
  </ThemeProvider>
</App>

// 或获取主题 token 用于四色同步
import { useToken } from '@lobehub/ui';
const { token } = useToken(); // antd Tokens

// Monaco Editor 主题同步 (代码编辑器)
function syncMonacoTheme(antdTokens: ThemeToken) {
  monaco.editor.defineTheme('openwork-theme', {
    base: 'vs-dark',
    inherit: true,
    colors: {
      'editor.background': antdTokens.colorBgContainer,
      'editor.foreground': antdTokens.colorText,
    },
    rules: [/* ... */],
  });
}

// @lobehub/editor 主题同步 (AI 输入编辑器)
function syncLobeEditorTheme(antdTokens: ThemeToken) {
  // Lexical 编辑器主题通过 CSS 变量注入
}

// xterm.js 终端主题同步
function syncTerminalTheme(antdTokens: ThemeToken) {
  const terminalTheme: ITheme = {
    background: antdTokens.colorBgElevated,
    foreground: antdTokens.colorText,
    cursor: antdTokens.colorPrimary,
  };
}
```

主题切换时，四个层（antd UI / Monaco / LobeHub editor / xterm）同步刷新，确保视觉一致。
