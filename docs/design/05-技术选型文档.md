### 0.4 选型原则

本项目选型遵循以下原则（按优先级降序）：

1. **生态成熟度**：优先选择社区活跃、长期维护、生产验证的方案
2. **类型安全**：TypeScript 一等公民，全栈类型共享
3. **本地优先**：数据主权在用户，零外部服务依赖
4. **LobeHub 生态对齐**：UI 层优先采用 LobeHub 官方生态，保证设计语言一致
5. **可观测可干预**：Agent 全链路可调试、可中断、可回放
6. **开源合规**：所有依赖许可证与 Apache-2.0 兼容
7. **性能与体验平衡**：不追求极致性能，但 UI 必须流畅（Worker 隔离保证）

## 1. 桌面框架

### 1.1 候选方案对比

| 候选 | 优势 | 劣势 | 成熟度 | 生态 | 许可证 | 推荐 |
|------|------|------|--------|------|--------|------|
| **Electron 35** | Node.js 原生集成；生态最成熟（VS Code/Discord/Slack）；npm 包直接可用；Worker Threads 崩溃隔离；自动更新成熟 | 安装包大（~80-150MB）；内存占用高（~150-300MB）；Chromium 体积 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | MIT | ✅ |
| **Tauri 2.x** | 安装包小（~5-15MB）；内存低（~50-100MB）；安全模型强（无 Node 暴露）；Rust 后端高性能 | 后端需 Rust（团队技能不匹配）；WebView 跨平台一致性差；JS 生态需 sidecar 桥接；插件生态远不及 Electron | ⭐⭐⭐⭐ | ⭐⭐⭐ | MIT/Apache | ❌ |
| **Neutralinojs** | 极轻量（~5MB）；零原生依赖；配置简单 | 生态极小；原生 API 有限；无 Worker 模型；社区薄弱；生产案例少 | ⭐⭐ | ⭐⭐ | MIT | ❌ |

**详细对比**：

| 维度 | Electron 35 | Tauri 2.x | Neutralinojs |
|------|:---:|:---:|:---:|
| 安装包大小 | ~80-150MB | ~5-15MB | ~5MB |
| 内存占用（空载） | ~150MB | ~50MB | ~30MB |
| 后端语言 | Node.js (JavaScript/TS) | Rust | C++/Go/扩展 |
| 渲染引擎 | Chromium（一致） | 系统 WebView（不一致） | 系统 WebView |
| Node.js 生态 | ✅ 原生 | ❌ 需 sidecar | ❌ 有限 |
| Worker Threads | ✅ 稳定 | ❌（Rust 线程） | ❌ |
| 自动更新 | electron-updater | 内置 tauri-updater | 第三方 |
| 原生 API 丰富度 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| 社区/StackOverflow | 海量 | 增长中 | 极少 |
| 生产级案例 | VS Code/Slack/Discord/Notion | 1Password/部分工具 | 极少 |
| npm 包兼容 | 100% | 部分（需 sidecar） | 极少 |

### 1.2 推荐方案

- **选型**: Electron 35.x（最新稳定版）
- **理由**:
  1. **Node.js 原生集成**：Agent 引擎用 TypeScript 实现，Electron Main Process 直接运行 Node.js，无需跨语言桥接，降低复杂度与 IPC 开销
  2. **生态最成熟**：better-sqlite3、simple-git、chokidar、isolated-vm 等关键原生依赖均为 Node.js 模块，Electron 原生支持
  3. **Worker Threads 崩溃隔离**：Agent Loop、工具执行、索引器运行于独立 Worker Thread，崩溃不影响 UI 渲染
  4. **Chromium 一致性**：跨平台渲染行为一致，避免 Tauri 系统 WebView（WebView2/WKWebKit/WebKitGTK）的差异导致的 CSS/JS 兼容问题
  5. **@lobehub/ui 生态验证**：LobeHub 全家桶在 Chromium 环境下渲染最佳，避免 WebView 差异
  6. **OpenCode 参考验证**：OpenCode 采用 TypeScript + Worker Thread 架构，已验证该路径可行
- **风险与缓解**:

| 风险 | 缓解措施 |
|------|----------|
| 安装包体积大（~150MB） | 使用 electron-builder 最大压缩；按平台分发；差量更新（electron-updater） |
| 内存占用高 | 主进程精简（App Shell 模式）；Agent/工具/索引运行于 Worker；闲置时释放 Worker |
| Chromium 安全更新滞后 | 跟随 Electron 主版本升级；CI 集成 CVE 扫描 |
| 启动速度 | 启用 Vite 代码分割；预加载关键模块；懒加载非首屏面板 |
- **版本锁定**: `electron ^35.0.0`
- **依赖包**:
```bash
npm install electron@^35.0.0
npm install -D electron-vite@^5.0.0 electron-builder@^25.0.0
```

### 1.3 集成要点

- **进程模型**：Main Process（App Shell + IPC 路由 + SQLite 连接池）+ Renderer Process（React UI）+ Worker Threads（Agent/Tool/Indexer/Plugin）
- **contextBridge 安全**：通过 `contextBridge.exposeInMainWorld` 暴露白名单 API，禁用 `nodeIntegration`，启用 `contextIsolation`
- **无边框窗口**：`frame: false` + 自定义 TitleBar，统一跨平台体验
- **自动更新**：`electron-updater` + GitHub Releases，支持差量更新与回滚
- **预加载脚本**：`preload/index.ts` 通过 `contextBridge` 暴露 IPC 客户端，类型定义共享于 `shared/types/ipc-channels.ts`
- **关键配置**：
```typescript
// electron-vite.config.ts
import { defineConfig } from 'electron-vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  main: { build: { rollupOptions: { input: 'src/main/index.ts' } } },
  preload: { build: { rollupOptions: { input: 'src/preload/index.ts' } } },
  renderer: {
    plugins: [react()],
    build: { rollupOptions: { input: 'src/renderer/index.html' } }
  }
});
```

## 2. 后端语言与运行时

### 2.1 候选方案对比

| 候选 | 优势 | 劣势 | 成熟度 | 生态 | 许可证 | 推荐 |
|------|------|------|--------|------|--------|------|
| **TypeScript 5.7 (Node.js)** | 与前端共享类型；npm 生态最大；Worker Threads 崩溃隔离；招聘容易；OpenCode 验证可行 | 性能不及 Rust/Go；单线程需 Worker 并行；内存占用较高 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | MIT/Node.js | ✅ |
| **Rust** | 极致性能；内存安全（所有权）；单二进制分发；async 生态（tokio）；Tree-sitter/sqlite-vec 原生支持 | 学习曲线高；招聘难；与前端类型共享需 codegen；编译时间长；与 LobeHub 生态断层 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | MIT/Apache | ❌ |
| **Go** | 编译快；并发原语（goroutine）优秀；单二进制；招聘较易；标准库强 | 泛型较弱；UI 生态弱；与 TS 类型共享需 codegen；LLM SDK 不及 Node 丰富；GC 停顿影响实时性 | ⭐⭐⭐⭐ | ⭐⭐⭐ | BSD-3-Clause | ❌ |

**详细对比**：

| 维度 | TypeScript 5.7 | Rust | Go |
|------|:---:|:---:|:---:|
| 性能（CPU 密集） | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 内存安全 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 并发模型 | Worker Threads + 事件循环 | async/await + tokio | goroutine |
| 与前端类型共享 | ✅ 原生（共享 .ts） | ❌ 需 ts-rs codegen | ❌ 需 codegen |
| LLM SDK 丰富度 | openai/anthropic 官方 | reqwest 手写 | 官方少 |
| 招聘难度 | 低 | 高 | 中 |
| 编译/启动速度 | 快（JIT） | 慢（编译） | 快 |
| 包管理 | npm | Cargo | go mod |
| 桌面框架契合 | Electron 原生 | Tauri 原生 | 有限 |
| OpenCode 参考验证 | ✅（双线程架构） | ❌ | ❌ |

### 2.2 推荐方案

- **选型**: TypeScript 5.7 + Node.js 22 LTS (Electron 内置) + Worker Threads
- **理由**:
  1. **全栈类型统一**：前后端共享 `shared/types/` 类型定义，IPC 通道、Agent 事件、工具定义全类型安全，零 codegen 开销
  2. **Node.js 生态最大**：better-sqlite3、simple-git、chokidar、isolated-vm、openai、@anthropic-ai/sdk、@modelcontextprotocol/sdk 等 LLM/MCP 关键依赖均为 Node.js 一等公民
  3. **Worker Threads 崩溃隔离**：Agent Loop、工具执行、索引器运行于独立 Worker，崩溃不影响 UI；这是 OpenCode 已验证的架构模式
  4. **招聘与贡献门槛低**：TypeScript 开发者基数最大，开源贡献门槛低，与 React 前端同一语言
  5. **Electron 原生**：Main Process 直接运行 Node.js，无需跨语言 IPC，降低复杂度
  6. **OpenCode 验证**：OpenCode 的 Agent Loop 设计（Tool.Info 模式、9 层编辑匹配、Doom Loop 检测）证明 TypeScript 在 AI Coding Agent 场景完全胜任
- **风险与缓解**:

| 风险 | 缓解措施 |
|------|----------|
| CPU 密集任务性能弱 | 运行于 Worker Thread 不阻塞 UI；Tree-sitter/SQLite 等原生模块承担重活 |
| 单线程瓶颈 | Worker Threads 多核并行；Agent/Tool/Indexer 独立 Worker |
| 内存占用 | Worker 闲置时终止；SQLite 连接池复用；流式处理避免全量缓存 |
| 类型擦除运行时错误 | Zod 运行时校验关键边界（IPC/配置/API 响应） |
- **版本锁定**:
  - `typescript ^5.7.0`
  - `node 22.x`（Electron 35 内置）
  - `@types/node ^22.0.0`
- **依赖包**:
```bash
npm install -D typescript@^5.7.0 @types/node@^22.0.0 tsx@^4.0.0
```

### 2.3 集成要点

- **Worker Threads 架构**（参考 08 文档方案 B）：
  - Agent Worker：PAOR 主循环 + Planning Loop + Prompt Engine + MCP Client
  - Tool Worker Pool：Shell 执行 + 文件操作 + Git 操作

### 10.2 推荐方案

- **选型**: web-tree-sitter（WASM 绑定）
- **理由**:
  1. **WASM 零编译**：无需 electron-rebuild，跨平台零配置，避免原生模块编译问题
  2. **Worker 兼容**：WASM 在 Worker Thread 中运行良好，索引器独立 Worker 不影响主进程
  3. **Tree-sitter 官方**：官方维护，与 VS Code/GitHub 等使用同一解析器
  4. **增量解析**：文件修改后只重新解析变更部分，索引更新 <5ms
  5. **50+ 语言**：覆盖所有主流编程语言
  6. **容错性强**：即使代码不完整/有语法错误，仍能产出部分 AST
  7. **S-expression 查询**：简洁强大的 AST 查询语言
- **风险与缓解**:

| 风险 | 缓解措施 |
|------|----------|
| WASM 加载配置 | Vite 配置 wasm 加载；预加载语言解析器 |
| 性能不及原生 | 索引在后台 Worker 执行不阻塞 UI；批量解析 |
| 语言解析器体积 | 按需加载语言 .wasm 文件；缓存到本地 |
- **版本锁定**: `web-tree-sitter ^0.25.0`
- **依赖包**:


### 10.3 集成要点

- **索引策略**：
  - 文件级：路径、语言、大小、依赖

### 12.2 推荐方案

- **选型**: isolated-vm（插件沙箱）+ Worker Threads（Agent/工具执行）
- **理由**:
  1. **双层隔离**：插件用 isolated-vm（V8 Isolate 级强隔离，内存/CPU 可限制），Agent/工具用 Worker Threads（崩溃隔离 + 多核并行）
  2. **isolated-vm 持续维护**：相比 vm2（2023 年停止维护，存在未修复安全漏洞），isolated-vm 持续维护，安全性更强
  3. **Worker Threads 原生**：Node.js 原生，npm 包可用，Agent Loop / 工具执行崩溃不影响 UI
  4. **OpenCode 参考验证**：OpenCode 采用 Worker Thread 架构验证 Agent 引擎可行性
  5. **Docker 远期企业版**：v1.0+ 企业版可选 Docker 容器沙箱（最强隔离）
- **沙箱分级**：

| 级别 | 方案 | 适用场景 | 隔离强度 |
|:---:|------|----------|:---:|
| L1 | Worker Threads + 路径白名单 | Agent Loop / 工具执行（默认） | 中 |
| L2 | isolated-vm（V8 Isolate） | 插件运行时 / Hooks（默认） | 强 |
| L3 | Docker 容器 | 企业版强化沙箱（可选） | 最强 |

- **风险与缓解**:

| 风险 | 缓解措施 |
|------|----------|
| isolated-vm 无 Node API | 通过 IPC 桥接文件系统/网络；插件声明权限 |
| Worker Threads 非完全隔离 | 路径白名单 + 权限网关 + 审计日志 |
| 原生模块编译 | electron-rebuild；预编译二进制 |
- **版本锁定**:
  - `isolated-vm ^5.0.0`
  - Worker Threads（Node.js 内置，无需安装）
- **依赖包**:
```bash
npm install isolated-vm@^5.0.0
```

### 16.2 HTTP 服务框架（后端 Transport 用）

**用途**：`packages/server` 的 `transports/http.ts`，提供 HTTP + SSE 传输层，供 `apps/web` 与远程客户端访问。

#### 16.2.1 候选方案对比

| 方案 | 仓库 | Stars | TypeScript | 性能 | 生态 | 维护状态 |
|------|------|:-----:|:----------:|------|------|:--------:|
| **Fastify** | fastify/fastify | 32k+ | ✅ 原生 | 极快（最块 Node.js 框架之一） | ⭐⭐⭐⭐⭐ | ✅ 活跃 |
| Express | expressjs/express | 65k+ | ✅ @types | 中等 | ⭐⭐⭐⭐⭐ | ✅ 维护中（偏慢） |
| Hono | honojs/hono | 20k+ | ✅ 原生 | 极快（边缘运行时优先） | ⭐⭐⭐⭐ | ✅ 活跃 |
| Koa | koajs/koa | 34k+ | ✅ @types | 中等 | ⭐⭐⭐ | ⚠️ 低活跃 |
| NestJS | nestjs/nest | 67k+ | ✅ 原生 | 中等（基于 Express/Fastify） | ⭐⭐⭐⭐⭐ | ✅ 活跃 |

#### 16.2.2 推荐方案

**Fastify**（`fastify` ^5.2.0）

**选型理由**：
1. **性能最优**：Node.js 生态最快的 HTTP 框架之一，JSON 序列化比 Express 快 2-3 倍
2. **TypeScript 原生**：内置类型推导，无需 @types
3. **插件生态完善**：`@fastify/cors`、`@fastify/websocket`、`@fastify/rate-limit` 等
4. **SSE 支持良好**：原生支持流式响应，适合 Agent 事件推送
5. **Schema 校验集成**：基于 JSON Schema 的请求/响应校验，与 JSON-RPC 契约契合
6. **轻量**：核心仅 HTTP 路由，不强制 DI / 装饰器，适合作为 Transport 层而非完整应用框架

> **不选 Express**：性能差距明显，且 TypeScript 支持需额外 @types。
> **不选 Hono**：虽性能优秀，但定位为边缘运行时（Cloudflare Workers/Deno），Node.js 场景生态不如 Fastify。
> **不选 NestJS**：过重，引入 DI 容器与装饰器模式，与 Transport 层定位不符。

#### 16.2.3 集成要点

```typescript
// packages/server/src/transports/http.ts
import Fastify from 'fastify';
import cors from '@fastify/cors';
import { JsonRpcRouter } from '../router';

export async function createHttpTransport(router: JsonRpcRouter) {
  const app = Fastify({ logger: true });

  await app.register(cors, { origin: true });

  // JSON-RPC 端点
  app.post('/rpc', async (request, reply) => {
    const result = await router.handle(request.body);
    return reply.send(result);
  });

  // SSE 事件流
  app.get('/events', async (request, reply) => {
    reply.raw.writeHead(200, {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
    });
    const unsubscribe = router.subscribe(event => {
      reply.raw.write(`data: ${JSON.stringify(event)}\n\n`);
    });
    request.raw.on('close', unsubscribe);
  });

  await app.listen({ port: 31750, host: '127.0.0.1' });
  return app;
}
```

#### 16.3.1 候选方案对比

| 方案 | 仓库 | Stars | TypeScript | 协议合规 | 性能 | 维护状态 |
|------|------|:-----:|:----------:|----------|------|:--------:|

#### 16.3.2 推荐方案

**ws**（`ws` ^8.18.0）+ `@fastify/websocket`（^11.0.0，与 Fastify 集成）

**选型理由**：
1. **标准合规**：严格遵循 RFC 6455 WebSocket 协议，与任意 WS 客户端互通
2. **性能最优**：Node.js 生态最快的 WebSocket 实现
3. **轻量**：无额外抽象层，适合作为 Transport 底层
4. **与 Fastify 集成**：`@fastify/websocket` 插件无缝接入

#### 16.3.3 集成要点

```typescript
// packages/server/src/transports/websocket.ts
import websocket from '@fastify/websocket';
import type { FastifyInstance } from 'fastify';
import { JsonRpcRouter } from '../router';

export async function registerWebSocketTransport(
  app: FastifyInstance,
  router: JsonRpcRouter,
) {
  await app.register(websocket);

  app.get('/ws', { websocket: true }, (socket, request) => {
    socket.on('message', async (data) => {
      const message = JSON.parse(data.toString());
      const result = await router.handle(message);
      socket.send(JSON.stringify(result));
    });

    // 推送事件到客户端
    const unsubscribe = router.subscribe(event => {
      socket.send(JSON.stringify({ type: 'event', payload: event }));
    });

    socket.on('close', unsubscribe);
  });
}
```

#### 16.5.4 已知问题与案例（M7 修复）

> **背景**：Turborepo 2.x + npm workspaces 在纯 Node.js monorepo 中成熟，但在 Electron 项目中（涉及 native 模块重编译、主进程/渲染进程分离构建、electron-vite 配置）的案例较少。本小节列出已知问题与缓解策略，供团队在 Phase 0 搭建时预先规避。

**已知问题 1：Electron native 模块 (better-sqlite3) 在 monorepo 中需 electron-rebuild 配置**

- **问题**：`better-sqlite3`、`node-pty`、`isolated-vm` 等 native 模块需针对 Electron 的 V8 ABI 编译，而非 Node.js 的 ABI。在 monorepo 中，`apps/desktop` 与 `packages/core` 可能共享 `node_modules`，导致 native 模块只针对 Node.js 编译，Electron 加载时崩溃。
- **缓解**：在 `apps/desktop/package.json` 的 `postinstall` 脚本中执行 `electron-rebuild`，并配置 `electron-builder` 的 `npmRebuild: false`（避免重复重编译）；或使用 `@electron/rebuild` 的 `--module-dir` 指向 monorepo 根 `node_modules`。
- **参考**：Electron 官方文档 [Using Native Node Modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules)。

**已知问题 2：Turborepo 缓存对 native 模块构建可能失效**

- **问题**：Turborepo 的缓存基于输入文件哈希（`inputs`）与输出目录（`outputs`）。native 模块的构建产物（`.node` 文件）依赖系统 ABI、Node.js/Electron 版本，但 Turborepo 默认不将这些环境变量纳入缓存键，可能导致缓存命中时返回错误 ABI 的二进制。
- **缓解**：在 `turbo.json` 的 `build` 任务中增加 `env` 字段，将 `NODE_VERSION`、`ELECTRON_VERSION`、`npm_config_arch` 纳入缓存键；或对 native 模块构建任务设置 `"cache": false`，强制每次重新编译。

**已知问题 3：apps/desktop 与 packages/core 的 dev 链接需 extra-watch 配置**

- **问题**：在 `dev` 模式下，`apps/desktop`（Electron 嵌入式）直接 import `@opencode/core`。Turborepo 的 `dev` 任务默认不 watch `packages/core` 的源码变更，导致后端代码修改后 Electron 不自动重启。
- **缓解**：在 `apps/desktop` 的 `electron-vite.config.ts` 中配置 `server.watch.extraWatchFiles`，将 `../../packages/core/src/**` 纳入监听；或使用 TypeScript Project References + `tsc --build --watch` 作为 `packages/core` 的 `dev` 任务，使 `apps/desktop` 通过类型引用感知变更。

**参考案例**

- 建议调研 Vercel Turborepo + Electron 社区实践，例如 [electron-vite + Turborepo 模板](https://github.com/topics/electron-turborepo)。
- Electron Forge 与 Nx 的集成案例可作为备选参考（若 Turborepo 集成本土化受阻）。
- v0.1 阶段建议以 `apps/desktop` + `packages/core` 的 dev 链接可用性为验收标准，再扩展到多客户端。

### 19.5 版本锁定要求与 SBOM（M6 修复）

> **背景**：本项目核心依赖已超 30 个（含 4 个 native/WASM 模块：`better-sqlite3` + `sqlite-vec` + `isolated-vm` + `web-tree-sitter`），加上 LobeHub 生态 8 个包，供应链风险较高。本小节明确版本锁定要求与 SBOM（Software Bill of Materials）生成策略。

**版本锁定要求**：

1. **精确版本锁定**：所有生产依赖（`dependencies`）与开发依赖（`devDependencies`）必须在 `package-lock.json` 中锁定到精确版本（`"version": "x.y.z"`），禁止使用 `latest` 标签或浮动版本范围。
2. **关键依赖版本约束**：以下关键依赖需在 `package.json` 中使用 caret 范围（`^x.y.z`）并在 `package-lock.json` 中锁定精确版本：
   - native 模块：`better-sqlite3`、`sqlite-vec`、`isolated-vm`、`web-tree-sitter`、`node-pty` — 升级需同步重编译验证
   - LobeHub 生态：`@lobehub/ui`、`@lobehub/editor`、`@lobehub/icons`、`@lobehub/lint` — 禁止使用 `latest`，必须锁定到具体版本（如 `@lobehub/editor` ^1.0.0）
   - 框架核心：`electron`、`react`、`vite`、`electron-vite` — 大版本升级需架构评审
3. **`package-lock.json` 提交到 Git**：确保可复现构建，CI 使用 `npm ci`（而非 `npm install`）安装依赖。
4. **依赖升级流程**：依赖升级需经 `npm audit` 通过后单独提 PR，禁止在功能 PR 中混入依赖升级。

**SBOM（Software Bill of Materials）要求**：

1. **构建时生成 SBOM**：每次构建/发布时自动生成 SBOM，记录所有依赖的版本/来源/许可证/哈希，用于安全审计与漏洞追踪。
2. **工具**：使用 `@cyclonedx/cyclonedx-npm`（CycloneDX 格式）或 `@npmcli/sbom`（SPDX 格式），详见 §21.1。
3. **CI 集成**：在 CI 流水线的 `build` 任务后追加 SBOM 生成步骤，SBOM 文件（`sbom/bom.json`）随发布产物归档。
4. **漏洞追踪**：当 CVE 公告发布时，通过 SBOM 快速定位受影响版本与依赖链路。

```bash
# 构建时生成 SBOM（CycloneDX 格式）
npm run build && npx @cyclonedx/cyclonedx-npm --output-file ./sbom/bom.json --output-format JSON

# 或使用 npm 内置 SBOM 命令（SPDX 格式）
npm run build && npm sbom --sbom-format spdx --sbom-type application --out ./sbom/bom.json
```

> **关联**：SBOM 生成与 CVE 扫描、签名构建的完整流程见 [§21 供应链安全](#21-供应链安全)。

## 21. 供应链安全

### 21.1 SBOM（软件物料清单）

**目标**：生成完整的 SBOM，记录所有依赖的版本/来源/许可证/哈希，便于漏洞追踪与合规审计。

**工具**：
- `cyclonedx-bom`（CycloneDX 格式）或 `@npmcli/sbom`（SPDX 格式）
- CI 集成，每次发布自动生成 SBOM

**实施**：
```bash
# 生成 CycloneDX SBOM
npx @cyclonedx/cyclonedx-npm --output-file ./sbom/bom.json --output-format JSON

# 生成 SPDX SBOM
npx @npmcli/sbom --sbom-format spdx --sbom-type application
```

**SBOM 存储与发布**：
- 每次发布版本附带 SBOM 文件（`sbom/bom.json`）
- 上传到 GitHub Release 附件
- 漏洞公告时快速定位受影响版本

### 21.2 CVE 漏洞扫描

**目标**：CI/CD 流水线自动扫描依赖漏洞，阻断高风险发布。

**工具**：
- `npm audit`（npm 内置）
- `audit-ci`（CI 集成，可配置阈值阻断）
- GitHub Dependabot（自动 PR 升级）
- GitHub Security Advisories

**实施**：
```bash
# 本地扫描
npm audit --audit-level=high

# CI 集成（阻断 high/critical）
npx audit-ci --high --moderate false
```

**CI 流水线集成**：
```yaml
# .github/workflows/security.yml
name: Security
on: [push, pull_request]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22' }
      - run: npm ci
      - run: npm audit --audit-level=high
      - run: npx audit-ci --high
      - run: npx @cyclonedx/cyclonedx-npm --output-file ./sbom/bom.json
```

**漏洞响应流程**：
1. Dependabot 自动 PR 升级
2. CI 阻断 high/critical 漏洞发布
3. 安全公告订阅（GitHub Security Advisories）
4. 紧急修复流程（24h 内发布补丁版本）

### 21.3 签名构建

**目标**：发布产物签名，用户可验证完整性与来源，防篡改。

**代码签名**：
- **macOS**：Developer ID Application 证书（Apple Notarization）
- **Windows**：EV Code Signing Certificate（SmartScreen 信任）
- **Linux**：GPG 签名（可选）

**electron-builder 签名配置**：
```yaml
# electron-builder.yml
win:
  certificateFile: ${CSC_LINK}
  certificatePassword: ${CSC_KEY_PASSWORD}
  signingHashAlgorithms: [sha256]
mac:
  identity: "Developer ID Application: OpenCoding Team"
  notarize:
    teamId: ${APPLE_TEAM_ID}
  hardenedRuntime: true
```

**产物校验**：
- 生成 SHA256 校验和（`sha256sum`）
- 发布到 GitHub Release
- 用户可验证：`sha256sum openwork-0.1.0.dmg`

**SBOM 签名**：
- SBOM 文件 GPG 签名
- 签名公钥发布到项目 README

### 21.4 供应链安全最佳实践

| 实践 | 实施 | 频率 |
|------|------|:---:|

### B.2 包管理变更影响（pnpm → npm）

> **关键变更**：设计契约 v4.0 明确要求使用 **npm**（非 pnpm）。以下是变更影响分析。

| 维度 | pnpm（废弃） | npm（v4.0 权威） | 影响 |
|------|:---:|:---:|------|
| 包存储 | 全局 store + 硬链接 | node_modules 扁平化 | 磁盘占用增加，但兼容性更好 |
| 幻影依赖 | 不存在（严格隔离） | 可能存在（hoisting） | 需严格声明依赖，禁用未声明包 |
| Electron 原生模块 | 需 `pnpmfile.cjs` 处理 | 原生兼容 | better-sqlite3/node-pty 编译更顺畅 |
| @lobehub/editor 链接 | 需特殊配置 | 原生解析 | 依赖解析问题减少 |
| Lock 文件 | `pnpm-lock.yaml` | `package-lock.json` | 迁移需删除旧 lock |
| CI 缓存 | `actions/setup-node` cache | `actions/setup-node` cache | 缓存 key 需更新 |
| Monorepo | workspace 协议 | npm workspaces | 语法略有差异 |

**迁移步骤**：

```bash
# 1. 删除 pnpm 产物
rm -rf node_modules pnpm-lock.yaml
rm -f .npmrc pnpmfile.cjs .pnpmfile.cjs

# 2. 使用 npm 重新安装
npm install

# 3. 提交 package-lock.json
git add package-lock.json
git commit -m "chore: migrate from pnpm to npm (v4.0 contract)"
```

**CI 配置更新**：

```yaml
# .github/workflows/ci.yml
- uses: actions/setup-node@v4
  with:
    node-version: '22'
    cache: 'npm'           # 非 pnpm
    cache-dependency-path: package-lock.json
- run: npm ci               # 非 pnpm install --frozen-lockfile
- run: npm run lint
- run: npm run test
- run: npm run build
```

**脚本统一**（package.json）：

```json
{
  "scripts": {
    "dev": "electron-vite dev",
    "build": "electron-vite build",
    "test": "vitest run",
    "test:e2e": "playwright test",
    "lint": "eslint . --ext .ts,.tsx",
    "format": "prettier --write .",
    "typecheck": "tsc --noEmit"
  }
}
```

> **禁止**：在文档、脚本、CI 中出现 `pnpm` 命令。所有安装命令统一为 `npm install` / `npm ci`。

## 文档结语

本文档为 OpenCoding 项目的**权威技术选型文档 v4.2**，覆盖 16 个技术域的候选方案对比、推荐方案与集成要点，并提供前端多客户端框架、LobeHub 生态集成、可复用开源项目分析、依赖版本锁定总表、许可证合规矩阵、供应链安全等专项章节。

**核心决策摘要**：

1. **桌面框架**：Electron 35（非 Tauri），Node.js 原生集成，生态最成熟
2. **后端语言**：TypeScript 5.7 + Worker Threads（非 Rust），全栈类型统一
3. **前端框架**：React 19.1，@lobehub/ui 原生支持
4. **UI 优先级**：@lobehub/ui base-ui 优先 → @lobehub/ui → 封装 → antd v6 兜底 → 自定义（禁止 antd 首选）
5. **双编辑器架构**：Monaco（代码编辑）+ @lobehub/editor（AI 交互输入）
6. **包管理**：npm（非 pnpm），设计契约 v4.0 锁定
7. **数据库**：better-sqlite3 + sqlite-vec + FTS5（+ LanceDB 可选）
8. **沙箱**：isolated-vm（插件）+ Worker Threads（Agent）（非 VM2）
9. **开源协议**：Apache-2.0，允许商业衍生
