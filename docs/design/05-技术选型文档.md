## 2. 桌面框架选型

### 2.1 候选方案对比

| 维度 | Tauri 2.x | Electron | Neutralino.js | Flutter Desktop |
|------|:---:|:---:|:---:|:---:|
| **安装包大小** | ~5MB | ~80MB+ | ~5MB | ~20MB |
| **内存占用 (空载)** | ~50MB | ~150MB+ | ~30MB | ~80MB |
| **后端语言** | Rust | Node.js | C++/Go | Dart |
| **性能** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| **安全模型** | 强 (CSP + 无 Node) | 弱 (Node 全权限) | 中 | 中 |
| **前端灵活性** | 任意前端框架 | 任意前端框架 | 任意前端框架 | Flutter Widget |
| **原生 API** | Rust 生态 | Node.js 生态 | 有限 | Dart FFI |
| **自动更新** | 内置 | electron-updater | 第三方 | 第三方 |
| **跨平台** | Win/Mac/Linux | Win/Mac/Linux | Win/Mac/Linux | Win/Mac/Linux |
| **社区成熟度** | 快速增长 | 最成熟 | 小众 | Google 支持 |
| **WebView** | 系统 WebView | Chromium | 系统 WebView | Skia |

### 2.2 选型决策

**选择: Tauri 2.x**

**核心理由**:

1. **体积与性能优势**: 安装包 < 25MB (vs Electron 80MB+)，内存占用低 60%+
2. **Rust 后端契合度**: 核心引擎 (Prompt/Context/Harness/Loop) 本身就是 Rust 实现，Tauri 后端天然集成
3. **安全模型**: 无 Node.js 运行时暴露，CSP + IPC 白名单，适合企业场景
4. **插件系统设计**: Tauri Plugin 体系支持自定义原生能力，便于 LSP/终端/编辑器桥接
5. **v2 版本成熟**: Tauri 2.x 已于 2024 年稳定，移动端支持 (远期扩展)

**风险与缓解**:

| 风险 | 缓解措施 |
|------|----------|
| WebView 兼容性差异 | 主要测试 Windows WebView2 / macOS WKWebView / Linux WebKitGTK |
| 原生功能需要 Rust 实现 | 插件 Worker 使用 Node.js 侧车进程弥补 JS 生态缺口 |
| 社区生态不及 Electron | 核心功能自研，UI 复用 Web 生态 |

## 3. 前端技术选型

### 3.1 框架选型

| 维度 | React 18 | SolidJS | Svelte 5 | Vue 3 |
|------|:---:|:---:|:---:|:---:|
| **生态规模** | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| **社区贡献者** | 最多 | 少 | 中 | 多 (中国强) |
| **TypeScript 支持** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| **性能** | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| **状态管理** | Zustand/Jotai | Signals 内置 | Runes 内置 | Pinia |
| **UI 库兼容** | 最多 | 有限 | 有限 | 中 |
| **学习曲线** | 低 | 中 | 低 | 低 |

**选择: React 18 + TypeScript**

**核心理由**: 生态最广、社区贡献者最多、UI 组件库最丰富 (shadcn/ui 首选 React)、降低开源项目贡献门槛。

**状态管理: Zustand**
- 轻量 (< 1KB)
- 基于 Hook，无 boilerplate
- 支持中间件 (persist, devtools, immer)

**备选方案 (如果未来性能瓶颈)**: SolidJS — 无虚拟 DOM，细粒度响应式，更适合大量实时更新的场景 (如 Loop Trace)。

### 3.2 UI 组件库

| 维度 | shadcn/ui | Radix UI | Mantine | Ant Design |
|------|:---:|:---:|:---:|:---:|
| **可定制性** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |

| **无障碍 (a11y)** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| **主题支持** | Tailwind 原生 | 需自建 | 内置 | 内置 |
| **组件数量** | 40+ | 30+ | 100+ | 60+ |
| **社区活跃** | 极高 | 稳定 | 中 | 高 (中国) |

**选择: shadcn/ui + Tailwind CSS**

**核心理由**:
1. 源码级定制: 组件代码复制到项目中，完全控制

4. 主题系统: Tailwind CSS 变量 + CSS 变量，完美支持自定义主题
5. 与 Tauri 搭配: 不引入额外运行时负担

## 4. 后端语言选型

### 4.1 核心引擎语言

| 维度 | Rust | Go | TypeScript (Node) | Python |
|------|:---:|:---:|:---:|:---:|
| **性能** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| **内存安全** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | ⭐⭐ |
| **并发模型** | async/await + 线程 | goroutine | 事件循环 | asyncio |
| **包管理** | Cargo (一流) | go mod | npm/pnpm | pip/poetry |
| **FFI 能力** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| **编译产物** | 单二进制 | 单二进制 | 需运行时 | 需解释器 |
| **学习曲线** | 高 | 低 | 低 | 低 |
| **招聘难度** | 中 | 低 | 低 | 低 |

**选择: Rust**

**核心理由**:

1. **性能与安全**: Agent 核心引擎需要高性能 + 内存安全，Rust 的所有权系统天然防止内存 bug
2. **Tauri 原生**: Tauri 后端就是 Rust，核心引擎可以直接嵌入
3. **单二进制分发**: CLI 版本可以直接 cargo build 为单二进制，零依赖分发
4. **并发优势**: async/await + tokio 生态，Agent 的多 Sub-Agent 并发、工具并发执行天然契合
5. **生态对齐**: Tree-sitter / sqlite-vec / LanceDB 等关键依赖都是 Rust 优先

**风险与缓解**:

| 风险 | 缓解 |
|------|------|
| 学习曲线高 | 核心引擎由资深 Rust 开发者维护，插件用 TS 降低贡献门槛 |
| 编译时间长 | sccache + 增量编译 + CI 缓存 |
| 招聘难度 | 开源社区吸引 Rust 爱好者；插件层用 TS 扩大贡献面 |

### 4.1.1 团队技能矩阵要求 (v0.1 MVP)

| 角色 | 人数 | 核心技能 | 水平要求 |
|------|:---:|------|------|
| Rust 核心开发 | 1-2 | Rust (tokio, async_trait, rusqlite), SQLite, LLM API 协议 | 高级: 2 年以上 Rust 经验，熟悉异步编程和 Send/Sync 边界 |
| 前端开发 | 1-2 | React 18, TypeScript, Tailwind CSS, CodeMirror 6, xterm.js | 中高级: 3 年以上前端经验，有桌面端或 IDE 开发经验优先 |
| 全栈/Tauri | 1 | Tauri 2.x, IPC 设计, Rust↔TS 桥接, 构建流水线 | 高级: 有 Tauri 或 Electron 桌面应用交付经验 |
| 产品/测试 | 1 | 产品需求, 测试策略, E2E 自动化 | 中级: 2 年以上 QA 经验，熟悉 Playwright |

**关键风险**: Rust 开发者招聘周期长 (通常 4-8 周)。建议核心团队至少 1 名已有 Rust 经验的成员，另一名可在项目中培养。

### 4.2 插件 Worker 语言

**选择: TypeScript (Node.js Worker Threads)**

**核心理由**:
1. JS/TS 生态最大，降低插件开发门槛
2. npm 包直接可用，无需重新实现
3. 与前端共享类型定义
4. 通过 IPC 与 Rust 核心通信，不影响核心稳定性

## 5. 数据库选型

### 5.1 主数据库

| 维度 | SQLite | PostgreSQL | MySQL | DuckDB |
|------|:---:|:---:|:---:|:---:|
| **部署复杂度** | 零 (嵌入) | 需服务 | 需服务 | 零 (嵌入) |
| **单文件存储** | ✅ | ❌ | ❌ | ✅ |
| **事务支持** | ✅ (ACID) | ✅ | ✅ | ✅ |
| **并发读写** | WAL 模式 | 原生支持 | 原生支持 | 有限 |
| **全文搜索** | FTS5 | 内置 | 内置 | 内置 |
| **向量扩展** | sqlite-vec | pgvector | ❌ | 内置 |
| **包大小** | < 1MB | > 100MB | > 100MB | ~15MB |
| **迁移友好** | ✅ (单文件复制) | 需 pg_dump | 需 mysqldump | ✅ |
| **客户端库** | rusqlite (Rust) | sqlx (Rust) | sqlx (Rust) | duckdb-rs |

**选择: SQLite (WAL 模式)**

**核心理由**:

1. **本地优先的完美匹配**: 零配置、零服务、单文件存储，与"本地优先、数据可迁移"的产品定位完全契合
2. **全量数据存储**: 配置/对话/记忆/Skills/MCP 配置/审计日志 全部存入 SQLite，一个文件包含所有数据
3. **迁移简单**: 用户只需复制 `.opencoding.db` 文件即可完成数据迁移
4. **WAL 模式**: 支持读写并发，Agent Worker 写 + UI 读不冲突
5. **rusqlite**: Rust 生态最成熟的 SQLite 绑定，性能优秀
6. **FTS5**: 内置全文搜索，无需额外搜索引擎

**数据量估算**:

| 数据 | 单条大小 | 频率 | 日增量 |
|------|:---:|------|:---:|
| 消息 | ~2KB | 50/会话 | ~100KB/会话 |
| 工具调用 | ~1KB | 20/会话 | ~20KB/会话 |
| Loop 步骤 | ~5KB | 50/会话 | ~250KB/会话 |
| 模型调用 | ~0.5KB | 50/会话 | ~25KB/会话 |
| 记忆 | ~1KB | 10/天 | ~10KB/天 |
| 审计日志 | ~0.5KB | 100/天 | ~50KB/天 |

**预估**: 重度用户 (10 会话/天) 日增量 ~5MB，年增量 ~2GB — SQLite 完全胜任。

### 5.2 SQLite 并发写入分析

**写入场景**:

| 写入方 | 数据 | 频率 | 优先级 |
|--------|------|:---:|:---:|
| Agent Worker | loop_steps, messages, checkpoints | 高 (每轮 PAOR 多次) | 关键 |
| Tool Worker | tool_calls, tool_results | 中 (每次工具调用) | 关键 |
| Indexer Worker | index_entries, index_meta | 低 (批量提交) | 可延迟 |
| Main/UI | configs, config_history | 极低 (用户手动) | 可延迟 |

**并发瓶颈分析**:

WAL 模式下，SQLite 支持并发读但写操作串行化。高负载场景下的风险:
- Agent Worker 写入 loop_steps 时，Tool Worker 需要等待锁释放才能写入 tool_calls
- 锁等待时间通常 < 1ms，但在高频写入场景 (如流式 token 每 chunk 都写) 会排队

**优化策略**:

| 策略 | 说明 | 实现 |
|------|------|------|
| **写入批量合并** | 多个小写入合并为一个事务 | Agent Worker 每轮 PAOR 完成后再写入 (非每 step) |
| **WAL 检查点调优** | 避免 WAL 文件过大 | `PRAGMA wal_autocheckpoint = 1000` (默认 1000 页 ≈ 4MB) |
| **busy_timeout 调优** | 写入排队时等待而非立即失败 | `PRAGMA busy_timeout = 5000` (5s 超时) |
| **WAL 检查点被动模式** | 避免检查点阻塞写入 | `PRAGMA checkpoint_fullfsync = OFF` (桌面端可接受) |
| **读写分离** | 高频读取使用独立只读连接 | 每个 Worker 持有 1 个写连接 + N 个只读连接池 |
| **流式写入节流** | 流式 token 不每 chunk 写入 | 每 500ms 或每 50 token 批量写入一次 |

**连接池设计**:

```rust
pub struct ConnectionPool {
    /// 写入连接 (单写者)
    write_conn: Mutex<Connection>,
    /// 只读连接池 (多读者)
    read_pool: Vec<Mutex<Connection>>,
}

impl ConnectionPool {
    /// 获取写连接 (互斥)
    pub fn write(&self) -> MutexGuard<Connection> {
        self.write_conn.lock().unwrap()
    }
    
    /// 获取只读连接 (轮询)
    pub fn read(&self) -> MutexGuard<Connection> {
        let idx = rand::random::<usize>() % self.read_pool.len();
        self.read_pool[idx].lock().unwrap()
    }
}
```

**结论**: SQLite WAL 模式 + 批量写入 + 连接池可满足桌面端单用户场景。如果未来需要多用户/Web 服务端部署，可迁移到 PostgreSQL (通过 Repository trait 抽象)。

## 7. 代码解析选型

### 7.1 语法解析器

| 维度 | Tree-sitter | ANTLR | Babel (JS) | Semgrep |
|------|:---:|:---:|:---:|:---:|
| **语言支持** | 50+ | 10+ | JS only | 30+ |
| **增量解析** | ✅ | ❌ | ❌ | ❌ |
| **容错性** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **性能** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| **Rust 绑定** | ✅ (原生) | ❌ | ❌ | ❌ |
| **AST 查询** | S-expression | Visitor | AST 遍历 | Pattern |

**选择: Tree-sitter**

**核心理由**:
1. **增量解析**: 文件修改后只重新解析变更部分，索引更新 < 5ms
2. **容错性强**: 即使代码不完整/有语法错误，仍能产出部分 AST
3. **50+ 语言**: 覆盖所有主流编程语言
4. **Rust 原生**: tree-sitter Rust 绑定性能优秀
5. **S-expression 查询**: 简洁强大的 AST 查询语言

### 7.2 LSP 集成

**选择: lsp-server (Rust) + 外部 LSP Server 桥接**

- 不内嵌 LSP Server (太重)，而是桥接到用户已有的 LSP Server
- 通过 stdio 与外部 LSP Server 通信
- 获取诊断/跳转/补全/悬停信息
- 主要采集诊断信息作为 Agent 上下文

## 9. 插件运行时选型

### 9.1 方案对比

| 维度 | Node.js Worker | WASM (wasmtime) | Deno | Python 子进程 |
|------|:---:|:---:|:---:|:---:|
| **JS/TS 生态** | ⭐⭐⭐⭐⭐ | ❌ | ⭐⭐⭐⭐ | ❌ |
| **npm 兼容** | ✅ | ❌ | ✅ (部分) | ❌ |
| **沙箱隔离** | Worker + isolated-vm | 原生 | 权限系统 | 进程隔离 |
| **性能** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **内存占用** | 中 | 低 | 中 | 高 |
| **启动速度** | 快 | 极快 | 中 | 慢 |
| **Rust 互操作** | 通过 IPC | 通过 wasmtime | 通过 IPC | 通过 IPC |

**选择: Node.js Worker Threads + isolated-vm 沙箱**

> **⚠️ 重要更新**: VM2 已于 2023 年因安全漏洞停止维护。改用 `isolated-vm` (v5+)，提供 v8::Isolate 级别的隔离，比 VM2 更安全且持续维护。

**核心理由**:
1. 最大 JS/TS 生态兼容性，npm 包直接可用
2. `isolated-vm` 提供 V8 Isolate 级别隔离，每个插件独立 Isolate，内存/CPU 可限制
3. 插件 SDK 可以用 TypeScript 编写，与前端共享类型
4. 作为 Tauri 的 sidecar 进程运行，不嵌入主进程

**备选**: 
- WASM (wasmtime) — 作为未来高性能/高安全插件的执行环境
- Deno subprocess — 内置权限系统，但生态兼容性不如 Node.js
