## 2. 架构师视角

> 关注点：架构能撑住吗？瓶颈在哪？扩展性好吗？

### 2.1 🔴 多进程架构缺乏故障恢复细节（严重）

**问题**: 04-§3.2 提到"崩溃影响"和"重启策略"，但缺少关键细节：
- Agent Worker 崩溃后，正在进行的 LLM 请求怎么办？(token 已消耗但无结果)
- 检查点恢复的**最大数据丢失窗口**是多少？
- 如果 Tool Worker 崩溃但 Agent Worker 期望工具结果怎么办？超时等待多久？

**涉及文档**: 04-架构设计文档.md §3.2、06-详细设计文档.md §3.1

**修改动作**: 
- 04-§3.2 增加故障恢复 SLA 表
- 06-§3.1 增加崩溃恢复状态机

### 2.2 🔴 Event Bus 缺少背压处理和消息持久化（严重）

**问题**: 04-§6 的 Event Bus 设计使用 Broadcast Channel，但：
- 没有背压处理：如果 UI 消费慢，Agent 事件堆积怎么办？
- 没有消息持久化：重启后事件丢失，无法恢复 Loop Trace 的最后状态
- 没有消息确认机制

**涉及文档**: 04-架构设计文档.md §6

**修改动作**: 增加背压策略、事件缓冲区、持久化事件队列的设计说明。

### 2.3 🟡 SQLite 并发写入瓶颈未充分分析（重要）

**问题**: 05-§5 提到 WAL 模式支持并发读写，但实际场景中：
- Agent Worker 写入 loop_steps（高频）
- Tool Worker 写入 tool_calls（中频）
- UI 读取 sessions/messages（高频）
- Indexer Worker 写入向量索引（低频）

WAL 模式下写操作仍然是串行的（单写者）。高负载场景下可能出现写入排队。缺少 WAL 检查点策略、busy_timeout 调优、以及可能的读写分离方案。

**涉及文档**: 05-技术选型文档.md §5、06-详细设计文档.md §3.10

**修改动作**: 
- 05-§5 增加"并发写入分析与优化"小节
- 06-§3.10 增加连接池和 WAL 检查点策略

### 2.4 🟡 缺少 gRPC/HTTP API 层的设计（重要）

**问题**: 当前架构只考虑了 Tauri IPC（桌面端）和 CLI。但如果未来需要：
- Web Dashboard 远程监控
- 第三方工具集成（CI/CD 调用 Agent）
- 团队协作服务器

目前完全没有 API 层的设计。

**涉及文档**: 04-架构设计文档.md §2、§5

**修改动作**: 在架构全景图中增加"可选 API Gateway 层"，标注为远期规划。

### 2.5 🟡 Prompt Engine 七层模型的 Token 预算分配未定义（重要）

**问题**: 06-§3.2 详细描述了七层模型的实现，但缺少每层的 Token 预算分配策略。如果 L6 (Dynamic Context) 膨胀，会挤压哪些层？优先级是什么？

**涉及文档**: 06-详细设计文档.md §3.2

**修改动作**: 增加 Token 预算分配表和各层的优先级与弹性范围。

### 2.6 🟢 插件沙箱 Node.js Worker 的安全性存疑（建议）

**问题**: 05-§9 选择 Node.js Worker Threads + VM2 沙箱。VM2 已停止维护（2023 年因安全漏洞被弃用）。应更新为 `isolated-vm` 或考虑 Deno 子进程沙箱。

**涉及文档**: 05-技术选型文档.md §9

**修改动作**: 更新沙箱方案为 `isolated-vm` 或 `Deno subprocess`，移除 VM2 引用。

## 3. 项目经理视角

> 关注点：v0.1 MVP 38 个 P0 需求，能按时交付吗？资源够吗？

### 3.1 🔴 MVP 范围过大，38 个 P0 需求不可行（严重）

**问题**: 02-§5.2 列出了 38 个 P0 需求。以一个 3-5 人核心团队估算：
- 每个 P0 需求平均需要 3-5 人天（含设计+开发+测试）
- 38 × 4 = 152 人天 ≈ 7.6 人月
- 加上集成、联调、Bug 修复，实际需要 10-12 人月
- 但路线图中 v0.1 应该是 2-3 个月的交付周期

**结论**: MVP 范围需要大幅削减到 15-18 个核心 P0 需求，其余降级为 P1。

**涉及文档**: 02-PRD产品需求文档.md §5.2、§6

**修改动作**: 
- 重新定义 MVP：只保留最核心的 18 个 P0 需求
- 将 Profile 系统、Hooks 系统、数据导入导出降级到 v0.2
- 增加资源估算表

### 3.2 🟡 缺少风险登记册（重要）

**问题**: 整个文档体系中没有任何风险评估和应对计划。对于一个全新产品，技术风险和市场风险都应该被识别。

**涉及文档**: 02-PRD产品需求文档.md（新增章节）

**修改动作**: 新增"§8 风险登记册"。

### 3.3 🟡 里程碑缺少明确的验收门禁（重要）

**问题**: 01-§6.2 的版本路线图只有"主题"和"核心交付"，缺少每个版本的**发布门禁**（如：通过哪些测试、性能达标、安全审计通过）。

**涉及文档**: 01-产品功能文档.md §6.2

**修改动作**: 为每个版本增加发布门禁标准。

### 3.4 🟡 非功能需求目标过于乐观（重要）

**问题**: 02-§4 的非功能目标：
- 冷启动 < 2s（含 SQLite 初始化 + 索引加载 + WebView 渲染）——非常激进
- 10 万文件首索引 < 60s —— 需要验证（向量嵌入非常耗时）
- 空闲内存 < 300MB —— Tauri + React + SQLite + 索引，300MB 可能不够

**涉及文档**: 02-PRD产品需求文档.md §4

**修改动作**: 调整性能目标为更现实的数值，标注"v0.1 目标"和"v1.0 目标"区分。

### 3.5 🟡 缺少研发团队技能矩阵要求（重要）

**问题**: 05-§4 提到 Rust 学习曲线高是风险，但缺少对团队的具体技能要求：需要几个 Rust 开发者？需要什么水平的？

**涉及文档**: 05-技术选型文档.md §4.1

**修改动作**: 增加"团队技能要求"小节。

## 5. 高级开发视角

> 关注点：这能实现吗？代码结构合理吗？有哪些技术债？

### 5.1 🔴 代码索引（Indexer Worker）的设计过于简略（严重）

**问题**: 代码库索引是整个产品的基础能力，但：
- 06 中完全没有 Indexer 的详细设计
- 04 中只有架构图中的一个框
- 增量索引的具体算法没有描述
- Tree-sitter 50+ 语言的语法文件如何管理？（每个语言 ~2-10MB，全部打包会很大）

**涉及文档**: 04-架构设计文档.md §4.3、06-详细设计文档.md（新增 §3.12）

**修改动作**: 
- 04-§4.3 增加 Indexer Worker 的详细架构
- 06 新增 Indexer 模块的详细设计

### 5.2 🔴 LLM 响应的工具调用解析缺少错误处理细节（严重）

**问题**: 06-§3.1 中 `act()` 方法直接匹配 `ChatResponse::Text` 或 `ChatResponse::ToolCalls`，但实际 LLM 响应可能是：
- JSON 格式错误（工具调用参数不是合法 JSON）
- 混合响应（部分文本 + 部分工具调用，GPT-4 常见）
- 工具调用名称不存在于 Registry
- 参数 Schema 校验失败

**涉及文档**: 06-详细设计文档.md §3.1

**修改动作**: 增加 `act()` 方法的异常处理分支，特别是工具调用解析的容错机制。

### 5.3 🟡 Rust 中的 async trait 兼容性问题（重要）

**问题**: 06 中大量使用 `#[async_trait]`，但 Rust 的原生 async trait（AFIT）在 1.75 才稳定，且仍有 Send/Sync 边界问题。大量使用 async_trait 宏会带来：
- 额外的 Box 分配
- Send/Sync 约束传播困难
- 调试困难

**涉及文档**: 06-详细设计文档.md §3（全局）

**修改动作**: 在文档中增加"Rust 异步模式说明"小节，说明使用 `#[async_trait]` 的原因和注意事项。

### 5.4 🟡 数据库迁移回滚未实现（重要）

**问题**: 06-§2.2 的 Migration 定义了 `down` SQL，但 `migrate()` 方法中没有实现回滚逻辑。如果迁移 3 失败，前面已成功的迁移 1 和 2 不会回滚（因为它们不在同一事务中）。

**涉及文档**: 06-详细设计文档.md §2.2

**修改动作**: 修复 `migrate()` 的事务范围，增加失败回滚机制。

### 5.5 🟡 缺少测试策略和测试金字塔（重要）

**问题**: 05-§10 列出了测试框架，但缺少：
- 测试金字塔结构（单元:集成:E2E 比例）
- Mock 策略（如何 Mock LLM Provider？如何 Mock 工具执行？）
- 核心模块的测试覆盖率目标

**涉及文档**: 05-技术选型文档.md §10

**修改动作**: 增加测试金字塔、Mock 策略、覆盖率目标。

### 5.6 🟡 配置热加载的竞态条件（重要）

**问题**: 06-§3.9 的 `set()` 方法在"发布 ConfigChangeEvent"和"各模块应用新配置"之间存在时间窗口。如果 Agent 正在执行 loop 的某个阶段，配置变更可能导致不一致的行为。

**涉及文档**: 06-详细设计文档.md §3.9

**修改动作**: 增加配置热加载的一致性保证机制（如：loop 边界生效、关键配置需重启）。

### 5.7 🟢 内存管理和资源释放（建议）

**问题**: 06-§3.1 的 `LoopEngineImpl` 持有多个 Arc 引用，但没有定义 Drop 行为和资源清理顺序。长时间运行的 Agent 可能导致内存泄漏。

**涉及文档**: 06-详细设计文档.md §3.1

**修改动作**: 增加资源管理和生命周期说明。

### 5.8 🟢 缺少错误处理的用户友好映射（建议）

**问题**: 06-§6.2 有错误码表，但错误码到用户友好消息的映射缺失。`E-AGENT-005` 对用户说"Agent 内部错误"是不够的。

**涉及文档**: 06-详细设计文档.md §6

**修改动作**: 增加错误码到用户消息的映射表。
