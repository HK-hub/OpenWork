## 0. 审视方法说明

### 0.1 自我否定式审视方法论

本次审视采用**自我否定式、自我批评式**方法，核心原则：

1. **假设有罪**: 默认每条架构决策都存在问题，需由"决策本身"举证其合理性，而非由"审视者"举证其错误。
2. **寻找反例**: 对每个"应当如此"的论断，主动构造反例场景 (尤其是多客户端、跨 Transport、崩溃恢复、企业部署场景)。
3. **不唱赞歌**: 本报告不写"该设计具有良好扩展性"等空泛赞美，只写"在 X 场景下会出现 Y 问题"。
4. **可追溯**: 每条问题引用具体文档章节与行号锚点，便于后续修复追踪。
5. **分级处置**: 每条问题标注严重度，区分"阻断交付"与"影响质量"。

### 0.2 审视角色与关注维度

## 2. 架构师视角 (Architect Perspective)

> 关注点：5 Transport 是否过度?9 层架构是否过深?Embedded 模式是否自相矛盾?11 模块依赖是否清晰?

### 2.1 🔴 Embedded Transport 模式与前后端分离架构自相矛盾 (严重)

**问题**: 04-架构 §3.2 层间依赖规则第 7 条明确写："**嵌入式模式下，L2 可直接 import L5 (绕过 L4)，但必须经 L3 类型契约约束**"。这等于说在默认运行模式 (04 §4.3.2 嵌入式为默认) 下：

- 前端 L2 客户端应用层直接 import 后端 L5 后端应用层；
- L4 Transport 层被绕过；
- "前后端通过 L3 API 契约与 L4 Transport 解耦"的核心架构原则在默认场景下失效。

更进一步：04 §4.3.2 嵌入式模式代码示例 `import { createBackend } from '@opencode/server'` 让前端直接持有后端句柄，等同于 v4.0 单体架构的 IPC 调用，并未真正分离。"前后端分离"在默认模式下名存实亡，仅在服务式模式 (04 §4.3.3) 下才成立。

**结论**: v4.1 架构对外宣称"前后端分离"，但默认运行模式是嵌入式，实际仍是单体。这导致：

- 多客户端共享后端的能力仅在服务式模式下可用，但服务式模式不是默认；
- 团队会优先按嵌入式开发 (因为简单)，后续切换到服务式时面临大量调试与序列化适配工作。

**涉及文档**: 04-§3.2 第 7 条 / 04-§4.3.1~§4.3.2 / 06-§3.13

**修改动作**:
1. 04 §3.2 第 7 条明确"嵌入式模式仅限 Desktop 单客户端场景，且必须通过 OpenCodeClient SDK 调用，禁止直接 import App Controller 内部类"；
2. 04 §4.3 重新定义默认模式：建议 v0.1 默认嵌入式、v0.2+ 默认服务式；
3. 06 §3.13 增加"嵌入式 vs 服务式切换的代码影响面"清单。

### 2.2 🔴 5 Transport 对 v0.1 过度设计，缺少降级路径 (严重)

**问题**: 04-§1.4、04-§4.1.2、06-§4.4 列出 5 种 Transport (HTTP+SSE / WebSocket / stdio / Electron IPC / Embedded)。但：

- 08 §10 MVP Phase 0 任务只列 "Transport 层骨架 (Embedded + IPC)" 两种；
- 06 §4.6~§4.10 为每种 Transport 各写了详细设计章节 (Fastify + SSE / ws / stdio / IPC / Embedded)，工作量巨大；
- 没有任何文档说明 5 种 Transport 的**优先级**与**降级路径**：如果 v0.1 只交付 2 种，其余 3 种何时补齐?未实现的 Transport 是否影响 API 契约层 (@opencode/api)?

**结论**: 5 Transport 是远期合理目标，但 v0.1 同步设计 5 套详细实现是过度工程。Transport 层抽象 (06 §4.4 TransportServer/TransportClient 接口) 是正确的，但具体实现应分阶段。

**涉及文档**: 04-§4.1.2 / 06-§4.6~§4.10 / 08-§10 Phase 0

**修改动作**: 06 §4.6~§4.10 增加标注："v0.1 实现: Embedded + IPC + stdio (3 种)；v0.2 实现: HTTP+SSE；v0.3 实现: WebSocket"；08 §10 Phase 0/1/2 明确每 Phase 交付的 Transport。

### 2.3 🔴 11 大 Harness 模块依赖图方向不明确，存在隐性循环风险 (严重)

**问题**: 04 §8.2 模块依赖关系图用箭头表示依赖，但箭头方向存在歧义：

- 图中模块 1 (Agent Loop Engine) 在顶部，箭头向下指向模块 4 (Context) / 3 (Tool) / 8 (Hooks)；
- 模块 6 (Plugin) / 7 (MCP) / 2 (Skill) 在中部，箭头向下指向模块 9 (Permission)；
- 模块 10 (Subagent) / 11 (Multi-agent) 在底部。

若箭头表示"依赖于"，则模块 1 依赖模块 3/4/8，但**模块 1 不依赖模块 10/11 (Subagent/Multi-agent)**，这与 04 §8.3 (Agent Loop Engine 调度子循环) 和 §8.12 (Subagent Manager 由 Agent Loop 调用) 的文字描述矛盾——Agent Loop 必然要调用 Subagent Manager 才能派生子 Agent。

若箭头表示"被依赖于"，则模块 10/11 被模块 6/7/2 依赖，这与"Subagent 调用 Plugin/MCP/Skill"的常识矛盾。

**真正的依赖关系**应该是: Agent Loop → Subagent Manager → Skill/Plugin/MCP → Tool → Permission，存在一条长链。若 Subagent 又需要回调 Agent Loop (派生子循环)，则形成 **Loop ↔ Subagent 循环依赖**。04 §8.2 没有说明该循环如何打破 (常见做法是引入事件总线或控制反转)。

**涉及文档**: 04-§8.2 / 04-§8.3、§8.12

**修改动作**: 04 §8.2 重画依赖图，明确箭头方向语义；新增"循环依赖打破策略"小节，说明 Agent Loop ↔ Subagent Manager 如何通过 Event Bus 或接口反转解耦。

### 2.4 🟡 9 层架构对 v0.1 过深，层间调用开销未评估 (重要)

**问题**: 04 §3.1 定义 9 层架构 (L1 表现 / L2 客户端应用 / L3 API 契约 / L4 Transport / L5 后端应用 / L6 Agent 核心 / L7 能力扩展 / L8 模型抽象 / L9 基础设施)。一次 agent.run 调用需穿越 L1→L2→L3→L4→L5→L6→L7→L9 至少 8 层 (04 §3.4 数据流图)。

04 §3.4 数据流图虽展示了流程，但**没有评估每层的延迟开销**。在嵌入式模式下，由于绕过 L4，可减少一层；但在服务式模式下，L4 序列化 + 网络往返 + L5 分发 + L6 Agent + L7 Tool + L9 SQLite 串行调用，单次工具调用的端到端延迟可能成为性能瓶颈。

**涉及文档**: 04-§3.1、§3.4

**修改动作**: 04 §3.4 增加延迟预算表 (各层处理时间 P50/P99)，并在 §3.5 各层职责矩阵中增加"是否可合并"列，标注 v0.1 可临时合并的层 (如 L7+L8)。

### 2.5 🟡 Transport 故障恢复仅覆盖连接断开，未覆盖协议级失败 (重要)

**问题**: 04 §4.5.1 故障恢复 SLA 表第 9 行仅处理"Client ↔ Backend 连接断开" (心跳超时 / socket close)，但未覆盖：

- **JSON-RPC 协议级错误**: method not found / invalid params / parse error 时客户端如何处理；

## 3. 技术总监视角 (CTO Perspective)

> 关注点：TypeScript-only 性能风险?isolated-vm V8 耦合?依赖数量?npm workspaces + Turborepo 可行性?

### 3.1 🔴 isolated-vm V8 版本耦合风险未充分评估 (严重)

**问题**: 04 §8.8 决策表 D6.6.1 仅一行注释"插件用 isolated-vm 沙箱 — V8 隔离，比 Worker Thread 更轻量，权限粒度细"，但未讨论 isolated-vm 的已知风险：

- **V8 版本耦合**: isolated-vm 必须与 Node.js 内置 V8 版本严格匹配，Node.js 升级时常需等待 isolated-vm 发新版，否则编译失败。本项目后端依赖 Node.js 22 LTS (06 §1.3)，每次 Node.js 小版本升级都可能触发插件沙箱编译失败；
- **Electron V8 差异**: Electron 35 内置 V8 版本与 Node.js 22 LTS 不同 (Electron 通常滞后或定制 V8)。在嵌入式模式下，后端跑在 Electron Main 进程内，使用 Electron 的 V8，此时 isolated-vm 必须用 Electron 的 V8 头文件编译 (需 `electron-rebuild`)；在服务式模式下，后端跑在独立 Node.js 进程，使用 Node.js 的 V8。**两种模式需要不同编译产物的 isolated-vm 二进制**，这一关键事实未在任何文档中说明；
- **沙箱崩溃恢复**: 04 §4.5.1 表中"Plugin Worker 崩溃"恢复策略写"手动重启"，意味着插件崩溃后无自动恢复，但 04 §8.8 又说插件是"生态扩展"核心。崩溃即不可用，与"生态"目标冲突。

**涉及文档**: 04-§8.8 D6.6.1 / 04-§4.5.1 / 06-§3.10 / 05-§12

**修改动作**:
1. 05 §12 增加 isolated-vm 风险小节 (V8 耦合、Electron 与 Node 双编译、ABI 兼容)；
2. 06 §3.10 增加"插件崩溃自动重启策略" (建议限流重启: 5 分钟内崩溃 3 次则标记 disabled)；
3. 04 §8.8 D6.6.1 补充"双编译产物"说明。

### 3.2 🟡 TypeScript-only 对索引/沙箱场景有性能风险 (重要)

**问题**: 04 §1.5 锁定全 TypeScript，但：

- **代码库索引**: 06 §3.3 ContextEngine + Indexer Worker 用 web-tree-sitter 解析代码。web-tree-sitter 是 WASM 版本，解析大代码库 (10w+ 文件) 的性能比 native tree-sitter 慢 3-5x。05 §10 未提供性能基准；
- **向量计算**: sqlite-vec 用 SQLite 扩展实现向量检索，但嵌入向量生成 (若本地) 仍需 TypeScript 计算，无 GPU 加速；
- **沙箱**: isolated-vm 虽是 native 模块，但插件代码本身是 JS，比 WASM 沙箱 (如 wasmtime) 性能低。

对标 OpenCode 用 Go 写后端、Cursor 用 Rust 做索引，本产品全 TS 在大规模代码库场景下可能成为性能瓶颈。但 04 §1.4 非功能目标只写"冷启动 < 3s / 空闲 < 400MB"，**没有索引吞吐量、向量检索延迟等关键性能指标**。

**涉及文档**: 04-§1.4、§1.5 / 05-§10 / 06-§3.3

**修改动作**: 04 §1.4 增加"索引吞吐量 > 100 文件/秒 (10w LOC 代码库 < 20 分钟)"、"向量检索 P99 < 50ms (100w chunks)"等指标；05 §10 增加 web-tree-sitter vs native tree-sitter 性能基准对比。

### 3.3 🟡 依赖数量过多，供应链风险高 (重要)

**问题**: 05 §0.3 列出的核心依赖已超 30 个，09 §0.1 再加 LobeHub 8 个包。关键风险：

**修改动作**: 09 §0.1 将 @lobehub/editor 版本从 latest 改为具体版本号；05 §21 增加 SBOM 生成 (建议 `npm sbom` 或 `cyclonedx-npm`) 与 CI 集成步骤。

**涉及文档**: 04-§1.4、§15 / 05-§16 / 08-§9

**修改动作**: 05 §16 增加"Electron + Turborepo 集成已知问题"小节；08 §9 增加 turbo.json 示例配置。

### 3.5 🟡 better-sqlite3 同步 API 在分离后端中是潜在瓶颈 (重要)

**问题**: better-sqlite3 是同步 API (06 §1.3 表格)。在 v4.0 单体架构下，SQLite 调用在 Main 进程，同步阻塞会影响 IPC；v4.1 分离后端后，SQLite 调用在后端进程主线程，同步阻塞会影响 JSON-RPC 分发 (L5)。

**涉及文档**: 04-§4.1.3、§4.2 / 06-§2.1

**修改动作**: 06 §2.1 增加"Worker 间 SQLite 访问策略"小节 (建议: 每个 Worker 各自打开只读连接 + 主进程持有写入连接，或所有写入经主进程 MessagePort 转发)。

## 5. 安全与合规视角 (Security Perspective)

> 关注点：权限网关多客户端适用性?服务式模式暴露风险?API Key 多客户端加密?插件沙箱?

### 5.1 🔴 服务式模式 HTTP/WS 暴露缺少认证与边界控制 (严重)

**问题**: 04 §4.3.3 服务式模式示例 `opencode-server --port 3456 --host 0.0.0.0`，监听 0.0.0.0 意味着对外网开放。但 04 §13 安全架构与 06 §3.5 PermissionGateway 均未说明：

- 服务式模式的**认证机制**: 客户端如何向服务式后端证明身份?04 §13 未定义 AuthPrincipal 的获取方式，06 §4.4.1 CallContext.auth 字段标 `?` (可选)；
- **TLS/HTTPS**: 04 §4.3.3 示例用 `http://`，未强制 `https://`，企业部署时 API Key、对话内容、代码片段均明文传输；
- **CORS / Origin 校验**: Web 客户端跨域访问服务式后端的 CORS 策略未定义；
- **Rate Limiting**: 服务式模式下多客户端共享后端，未定义单客户端调用频率上限，存在滥用风险；
- **WebSocket Origin 校验**: ws 8.x 默认不校验 Origin，需手动配置，06 §4.7 未提及。

**结论**: 服务式模式若按当前文档直接部署，等于把 Agent 引擎 (可执行任意工具) 暴露在网络上无认证保护，是高危安全漏洞。

**涉及文档**: 04-§4.3.3、§13 / 06-§3.5、§4.4.1、§4.7

**修改动作**:
1. 04 §13 增加"服务式模式认证"小节 (建议: Bearer Token + TLS 强制 + Origin 白名单)；
2. 06 §4.7 增加 WebSocket Origin 校验代码示例；
3. 04 §4.3.3 示例改为 `--host 127.0.0.1` 默认，`--host 0.0.0.0` 需显式加 `--allow-remote` 标志且强制 TLS。

### 5.2 🟡 多客户端权限审批缺乏并发一致性机制 (重要)

**问题**: 06 §4.3 事件清单中 `tool.approval_needed` 与 `permission.requested` 推送给客户端，客户端返回 `permission.decision` (04 §4.4.2)。但在多客户端场景 (服务式模式 + Web + CLI 同时连接)：

- **审批竞争**: 同一破坏性操作触发审批，多个客户端同时响应可能产生冲突决策 (一个批准一个拒绝)；
- **审批归属**: 哪个客户端有权限审批?是否有"主客户端"概念?04 §4.1.1 说"多客户端平等无特权"，但平等意味着任何客户端都能审批，与安全最小权限原则冲突；
- **审批超时**: 若发起审批后所有客户端都未响应，超时后默认拒绝还是放行?04 §13 与 06 §3.5 未定义。

**涉及文档**: 04-§4.1.1、§13 / 06-§3.5、§4.3

**修改动作**: 06 §3.5 增加"多客户端审批一致性"小节 (建议: 审批发起时锁定到第一个响应的客户端，其余客户端仅可查看；超时默认拒绝；引入审批令牌防重放)。

### 5.3 🟡 API Key 加密在多客户端配置同步下需重新评估 (重要)

**问题**: 04 §13 提到 "API Key Vault" 横切关注点，06 §3.x 应有 API Key 加密设计 (但 06 §3 核心模块清单未单独列出 API Key Vault 模块)。多客户端场景下：

- API Key 存储在后端 SQLite (加密)，前端不持有 — 这是正确的；
- 但 04 §4.1.1 客户端职责边界写"❌ 直接调用 LLM Provider API"，意味着所有 LLM 调用经后端，API Key 不出后端；

## 6. 高级开发视角 (Senior Developer Perspective)

> 关注点：JSON-RPC 跨 Transport 调试?29 表复杂度?Transport 集成测试?热重载?TS 项目引用?

### 6.1 🔴 JSON-RPC 跨 Transport 调试工具缺失 (严重)

**问题**: 04 §14 可观测性架构与 06 §7 测试策略均未定义"如何调试 JSON-RPC 跨 Transport 调用"。开发者面对的实际场景：

- Desktop 嵌入式模式下，Renderer → IPC → Main → Direct call → Backend，任一环节出错 (参数序列化失败、AsyncIterable 中断、IPC 句柄泄漏) 都会导致调试困难；
- 服务式模式下，Client → HTTP/SSE → Backend，流式响应中途断开时，开发者如何判断是网络问题还是后端 Loop Engine 异常?
- 06 §4.3 提到 `event.subscribe` 与 ring buffer，但未定义"如何查看 ring buffer 内容"的调试接口；
- 04 §14 提到 Loop Trace 调试器，但仅覆盖 Agent Loop 层，未覆盖 Transport 层。

**结论**: 缺少 Transport 层调试工具，开发者将被迫用 `console.log` 在 5 种 Transport 实现中分别打日志，效率极低。

**涉及文档**: 04-§14 / 06-§4、§7

**修改动作**:
1. 04 §14 增加"Transport 调试器"小节 (建议: JSON-RPC 消息录制 + 回放工具，类似 Chrome DevTools Network 面板)；
2. 06 §4 增加 `debug.rpc.trace` 调试事件，所有 Transport 实现统一发布；
3. 06 §7 增加 Transport 调试测试用例。

### 6.2 🟡 29 表 Schema 对 v0.1 复杂度过高，缺少分阶段迁移 (重要)

**问题**: 06 §2.1 一次定义 29 张表，§2.4 Migration Manager 虽提到迁移脚本但未分阶段。v0.1 若只交付 4 模块 (Loop/Tool/MCP/Permission，见 §4.2)，实际需要的表约 10~12 张 (sessions / messages / tool_calls / audit_log / permission_decisions / model_calls / config / profiles / checkpoints / index_meta)，其余 17 张表 (subagents / multiagent / memory_* / skills / plugins / hooks / personas / cost_records / vector_chunks / ftx_* / event_log 等) 在 v0.1 创建但无写入，徒增 Schema 复杂度与初始迁移时间。

**涉及文档**: 06-§2.1、§2.4

**修改动作**: 06 §2.1 增加"v0.1 必需表 (10~12 张) vs v0.2+ 表 (17 张)"分组；§2.4 Migration Manager 支持按版本阶段建表。

### 6.3 🟡 Transport 集成测试策略过于简略 (重要)

**问题**: 06 §7 测试策略表格仅一行 "Transport 集成 — 端到端 JSON-RPC over 各 transport — Vitest — 5 种 transport 跑同一套方法用例 (参数化)"，并备注"WS 与 HTTP 共用 ws 实现，合并测试"。但：

- 未定义**多客户端并发测试** (同一后端被 4 客户端同时调用 agent.run 的行为)；
- 未定义**流式响应中断恢复测试** (SSE 流中途断开后客户端如何恢复)。

**涉及文档**: 06-§7

**修改动作**: 06 §7 扩展为独立小节，增加故障注入矩阵、多客户端并发用例、流式中断恢复用例。

### 6.4 🟡 Monorepo 热重载策略未明确 (重要)

- 每个包的 `tsconfig.json` 需 `composite: true`；

**涉及文档**: 04-§15 / 06-§4.11

### 8.3 总体结论

v4.1 前后端分离架构在**长期愿景上是合理的** (对标 OpenCode/Codex 的多客户端形态)，但在**v0.1 范围内是过度承诺的**：

1. **范围与资源不匹配**: 4 客户端 + 5 Transport + 11 模块 + 29 表 + 8 周，任一维度都偏紧，叠加后不可能按期交付；
2. **默认模式与目标矛盾**: 嵌入式默认模式实际是单体，"前后端分离"在 v0.1 名不副实；
3. **跨文档契约不一致**: P0 数量、项目名、Rust/pnpm 残留、版本号引用等问题表明文档集缺乏统一校对；
4. **关键风险未覆盖**: isolated-vm 双编译、服务式认证、Transport 调试、回退方案等工程必须项缺失。

**建议**: v0.1 收缩为 "Desktop (嵌入式) + 4 模块 (Loop/Tool/MCP/Permission) + 12 表 + 6 周"，将多客户端、服务式、Web/TUI/CLI、Subagent/Multi-agent 推迟到 v0.2~v0.3。这样既符合 8 周内可交付，又保留 v4.1 架构演进的余地。

### 8.4 修复后结论 (v2.1 新增)

上述 §8.3 建议已被采纳并落地。经过两批修复 (详见 §8.0 修复状态追踪表)，设计文档集已升级至 **v4.2 基线**：

1. **范围已收缩**: v0.1 明确为 "Desktop (嵌入式) + 4 模块 + 12 表 + 6-8 周 + 3 Transport (Embedded/IPC/stdio)"；多客户端/服务式/Web/TUI/CLI/Subagent/Multi-agent 推迟至 v0.2 (Week 9-12) 与 v0.3 (Week 13-16)；
2. **前后端分离重新定义**: v0.1 为"逻辑分离"(包结构 @opencode/core/@opencode/api/@opencode/server + JSON-RPC 契约)，v0.2+ 才提供物理进程分离 (Service/Subprocess 模式)；
3. **跨文档契约已统一**: P0=19 项、项目名 OpenCoding、版本号 v4.2 基线、模块口径 11 大顶层 + 17 子模块映射表，全文档集一致；
4. **关键风险已覆盖**: isolated-vm 双编译回退方案、服务式安全基线 (TLS/Bearer/Origin)、Transport 调试器 (TransportTracer+RpcReplayer)、4 项回退方案 (JSON-RPC/isolated-vm/sqlite-vec/Turborepo) 均已补齐。

**当前状态**: 39 项改进点中 37 项已修复 (94.9%)，剩余 2 项 🟢 建议项 (L1 北极星指标、L5 审计日志 append-only 触发器) 排入 Backlog，不影响 v0.1 启动。设计文档集已具备启动 v0.1 实施的条件。
