## 1. 文档定位

本文档对每个功能模块进行**详细功能规格描述**，包含：输入/输出、前置条件、后置条件、交互流程、状态变化、异常处理。面向研发工程师和 QA，是编码和测试的直接依据。

v2.1 起，功能规格覆盖多种客户端类型（Desktop / TUI / Web / CLI），不再仅限于桌面端。所有客户端均为瘦客户端，通过 JSON-RPC 2.0 Transport 层与后端 Server 通信，核心 Agent 引擎与业务逻辑统一由后端 @openwork/core、@openwork/server 承载。

## 2. 核心功能规格

### 2.1 Agent 核心引擎

#### 2.1.1 PAOR 主循环

```
功能编号: F-AGENT-001
功能名称: PAOR 主循环
优先级: P0
```

**功能描述**:
Agent 核心循环按 Perceive → Act → Observe → Reflect 四个阶段循环执行，直到满足终止条件。

**输入**:
- `TaskInput`: 用户输入的任务描述 (文本/多模态)
- `SessionContext`: 当前会话上下文
- `LoopConfig`: 循环配置参数

**输出**:
- `Stream<AgentEvent>`: 事件流 (实时推送到 UI)
- `SessionState`: 最终会话状态

**事件类型**:

| 事件 | 阶段 | 携带数据 |
|------|:---:|----------|
| `loop:start` | 循环开始 | session_id, iteration_count |
| `perceive:start/end` | 感知 | assembled_context, token_count |
| `act:start` | 行动开始 | - |
| `act:tool_call` | 工具调用 | tool_id, tool_name, args |
| `act:tool_result` | 工具结果 | tool_id, result, duration_ms |
| `act:llm_response` | LLM 纯文本 | text_chunk (流式) |
| `observe:start/end` | 观察 | parsed_observation |
| `reflect:start/end` | 反思 | self_assessment, plan_update |
| `loop:end` | 循环结束 | termination_reason |
| `loop:error` | 错误 | error_type, error_message |

**前置条件**:
- 有效的 LLM Provider 配置
- 至少一个可用工具 (可选，纯文本回答不需要工具)

**后置条件**:
- 会话状态已持久化到数据库
- Loop Trace 已记录

**主流程**:

```
1. [Perceive]
   1.1 调用 ContextEngine.assemble(session_id, task_input) 组装上下文
   1.2 调用 PromptEngine.build(session_context, task_input) 组装 Prompt
   1.3 检查 Token 预算，必要时触发压缩
   1.4 发射 perceive:end 事件

2. [Act]
   2.1 调用 ModelProvider.chat(messages, tools, config) 获取 LLM 响应
   2.2 如果响应包含 tool_calls:
       2.2.1 对每个 tool_call:
             a. 发射 act:tool_call 事件
             b. 经 PermissionGateway 校验
             c. 经 ToolDispatcher 路由到 Worker
             d. 在 Sandbox 中执行
             e. 记录审计日志
             f. 发射 act:tool_result 事件
       2.2.2 将工具结果追加到消息历史
   2.3 如果响应是纯文本: 流式输出到 UI

3. [Observe]
   3.1 解析工具输出为结构化 Observation
   3.2 写入工作记忆
   3.3 发射 observe:end 事件

4. [Reflect] (每 reflection_interval 轮触发)
   4.1 构造反思 Prompt: "评估当前进度，是否偏离目标？"
   4.2 LLM 自评
   4.3 如果偏离: 触发重规划
   4.4 发射 reflect:end 事件

5. 检查终止条件:
   - 任务完成 (LLM 声明或工具结果指示)
   - 达到 max_iterations
   - 用户停止
   - 成本超限
   - 不可恢复错误
   → 满足则退出，否则回到 1
```

**异常处理**:

| 异常 | 处理 |
|------|------|
| LLM API 调用失败 | 自动 Fallback 到备选模型，重试最多 3 次 |
| 工具执行超时 | 返回 timeout 错误给 LLM，不中断循环 |
| 工具执行异常 | 返回结构化错误给 LLM，触发 Recovery Loop |
| Token 超预算 | 触发上下文压缩 |
| 用户中断 | 保存检查点，退出循环 |
| 不可恢复错误 | 退出循环，通知用户 |

**配置项**:

```yaml
loop:
  max_iterations: 50
  reflection_interval: 5
  planning:
    auto_plan_threshold: 3
    require_user_approve_plan: false
  verification:
    auto_run_tests: true
    auto_lint: true
    auto_typecheck: true
  recovery:
    max_retries: 3
    on_persistent_failure: "ask"
  hitl:
    mode: "key_nodes"
    confirm_on: [delete, run_command, force_push]
  checkpoint:
    enabled: true
    interval: "every_step"
```

#### 2.1.2 Planning Loop 子循环

```
功能编号: F-AGENT-002
功能名称: Planning Loop 子循环
优先级: P0
```

**功能描述**:
当任务复杂度超过阈值时，Agent 先产出结构化任务计划 (DAG)，经用户审批后执行。

**触发条件**:
- `estimated_steps > planning.auto_plan_threshold` (默认 3)
- 或用户显式使用 `/plan` 命令

**输入**:
- `TaskDescription`: 用户任务描述
- `ProjectContext`: 项目上下文

**输出**:
- `TaskPlan`: 包含子任务 DAG 的结构化计划
- `PlanApproval`: 用户审批结果

**TaskPlan 数据结构**:

```typescript
interface TaskPlan {
  id: string;
  title: string;
  description: string;
  tasks: PlanTask[];
  dependencies: TaskDependency[];  // from_task_id -> to_task_id
  estimated_total_steps: number;
  estimated_total_tokens: number;
  created_at: number;
}

interface PlanTask {
  id: string;
  title: string;
  description: string;
  status: 'pending' | 'running' | 'completed' | 'failed' | 'skipped';
  assigned_agent: string | null;  // Sub-Agent ID, null = 主 Agent
  estimated_steps: number;
  tools_required: string[];
  priority: number;  // 越小越优先
}
```

**主流程**:

```
1. 构造规划 Prompt (含任务描述 + 项目上下文)
2. LLM 产出 TaskPlan (JSON 结构化输出)
3. 展示给用户: 任务树 + 依赖图 + 预估步数/成本
4. 用户操作:
   - 批准: 进入 Execution Loop
   - 修改: 编辑计划 → 重新展示
   - 调整优先级: 拖拽排序 → 重新计算依赖
   - 拒绝: 回到自由对话模式
5. 计划保存到数据库
```

**UI 交互规格**:

- 任务树组件: 树形展示，每节点显示状态图标 (⏳/🔄/✅/❌)
- 依赖图组件: DAG 可视化，箭头表示依赖关系
- 进度条: 整体完成百分比
- 操作按钮: 批准/修改/拒绝/调整优先级
- 预估信息: 步数/Token/成本/时间

**异常处理**:

| 异常 | 处理 |
|------|------|
| LLM 产出格式不合法 | 重试最多 3 次，仍失败则降级为自由模式 |
| 计划过于复杂 (>50 子任务) | 提示用户简化任务 |
| 用户长时间不审批 (5 分钟) | 超时提示 |

#### 2.1.3 Sub-Agent 派生

```
功能编号: F-AGENT-003
功能名称: Sub-Agent 派生与协作
优先级: P1
```

**功能描述**:
主 Agent 可派生隔离子 Agent 处理独立子任务，支持主从/并行/专家三种模式。

**Sub-Agent 定义**:

```typescript
interface SubAgentConfig {
  id: string;
  name: string;
  persona: string;           // System Prompt 角色描述
  model_override?: string;   // 可覆盖模型
  tools: string[];           // 工具白名单
  skills: string[];          // Skills 列表
  max_iterations: number;
  context_isolation: true;   // 强制上下文隔离
  budget_limit_usd: number;  // 成本上限
}
```

**派生流程**:

```
1. 主 Agent 调用 task_spawn(sub_agent_id, task_description)
2. 引擎创建 Sub-Agent 实例:
   - 独立的上下文窗口 (context_isolation=true)
   - 工具白名单过滤
   - Persona 注入 System Prompt
   - 子预算分配
3. Sub-Agent 独立执行 PAOR 循环
4. 完成后返回结构化结果给主 Agent:
   {
     status: "completed" | "failed" | "timeout",
     summary: string,
     artifacts: Artifact[],
     token_used: number,
     cost_usd: number
   }
5. 主 Agent 将结果注入 Observation
```

**并发控制**:

- 最大并行 Sub-Agent 数: `loop.sub_agent.max_parallel` (默认 4)
- 超限时排队等待
- 总预算 = 父任务预算 - 已消耗 + 子任务预算 (父任务预算联动)

**通信协议**:

```
主 Agent → Sub-Agent:
{
  type: "task_assign",
  task_id: string,
  description: string,
  context_snapshot: string,  // 仅摘要，不共享完整上下文
  deadline_steps: number
}

Sub-Agent → 主 Agent:
{
  type: "task_result",
  task_id: string,
  status: "completed" | "failed" | "timeout",
  summary: string,
  artifacts: Artifact[],
  token_used: number,
  cost_usd: number,
  errors: ErrorDetail[]
}
```

### 2.2 动态结果调整系统

```
功能编号: F-CHAT-002
功能名称: 动态结果调整
优先级: P0 (核心亮点)
```

**功能描述**:
用户可在 Agent 执行过程中任意时刻修改对话内容、工具结果或 Agent 决策，动态调整执行路径，无需打断重新开始。

**支持的调整类型**:

#### 2.2.1 消息编辑

```
操作: 编辑已发送的用户消息或 Agent 回复
前置条件: 消息已存在于会话历史中
交互: 点击消息 → 进入编辑模式 → 修改内容 → 点击"从此处继续"
后置条件:
  - 原消息标记为 edited，保留原始版本
  - 从编辑位置之后的所有消息标记为 stale
  - Agent 从编辑后的位置重新继续
```

#### 2.2.2 工具结果修改

```
操作: 修改工具调用的返回结果
前置条件: 工具已执行完毕，结果已返回
交互: 展开工具调用详情 → 点击"编辑结果" → 修改内容 → 点击"应用"
后置条件:
  - 原始结果保留在 tool_calls 表中 (original_result 字段)
  - 新结果写入 modified_result 字段
  - Agent 使用修改后的结果继续
  - 该修改记录到审计日志
```

#### 2.2.3 决策干预

```
操作: 修改 Agent 下一步选择的工具或参数
前置条件: Agent 已决定调用某个工具但尚未执行
交互: 在 Loop Trace 中点击当前步骤 → 修改 tool_name 或 args → 点击"继续"
后置条件:
  - Agent 使用修改后的工具和参数执行
  - 原始决策保留在 loop_steps 表中
```

#### 2.2.4 上下文注入

```
操作: 在任意步骤注入额外上下文信息
前置条件: 当前在 Loop 执行中
交互: 点击"注入上下文"按钮 → 输入/选择内容 → 确认
后置条件:
  - 注入内容追加到当前上下文
  - 标记来源为 user_injected
  - Agent 在下一步感知到新上下文
```

#### 2.2.5 分支探索

```
操作: 从历史某步 fork 出新会话探索不同路径
前置条件: 会话有至少一个步骤
交互: 右键步骤 → "从此处分支" → 新会话标签页打开
后置条件:
  - 新会话的 fork_from 字段指向原会话和步骤
  - 两个会话独立发展，互不影响
  - 分支关系可视化在会话分支树中
```

#### 2.2.6 回退重试

```
操作: 回退到历史某步，修改输入后重新执行
前置条件: 会话有至少一个步骤
交互: 点击步骤 → "回退到此" → (可选)修改该步内容 → "重新执行"
后置条件:
  - 该步之后的消息标记为 stale
  - Agent 从该步重新执行
  - 原执行路径保留在历史中 (可恢复)
```

**数据模型**:

```sql
-- 消息表增加编辑追踪
ALTER TABLE messages ADD COLUMN original_content TEXT;  -- 编辑前的原始内容
ALTER TABLE messages ADD COLUMN edited_at INTEGER;      -- 编辑时间
ALTER TABLE messages ADD COLUMN is_stale BOOLEAN DEFAULT 0;  -- 是否因回退/分支而过期

-- 工具调用表增加结果修改追踪
ALTER TABLE tool_calls ADD COLUMN original_result TEXT;   -- 原始结果
ALTER TABLE tool_calls ADD COLUMN modified_result TEXT;   -- 用户修改后的结果
ALTER TABLE tool_calls ADD COLUMN modified_by TEXT;       -- 修改者
ALTER TABLE tool_calls ADD COLUMN modified_at INTEGER;    -- 修改时间

-- 分支关系
ALTER TABLE sessions ADD COLUMN fork_from_session_id TEXT;
ALTER TABLE sessions ADD COLUMN fork_from_step_id TEXT;
```

**UI 交互规格**:

- 每条消息/每个工具调用旁显示"编辑"按钮
- 编辑模式: 原地变为输入框，保留原始格式
- 修改后消息旁显示"已编辑"标记，点击可查看原始版本
- 分支树面板: 树形可视化展示会话分支关系
- 回退操作有确认弹窗: "将丢弃 X 步之后的内容，确定？"

**边缘场景处理**:

#### 场景 1: 修改工具结果后 Agent 不按预期走

```
问题: 用户修改了工具返回的代码搜索结果，但 Agent 基于修改后的结果做出了错误的后续判断。

处理:
1. 修改结果后，Agent 重新执行 Observe → Reflect → Act (从当前步继续)
2. 如果 Agent 行为异常，用户可:
   a. 再次编辑该工具结果 (版本链: 原始 → v1 → v2 → ...)
   b. 回退到该步骤，选择"不修改，使用原始结果"
   c. 分支探索: fork 一个新会话测试不同修改方案
3. UI 提示: "已修改工具结果，Agent 将基于新结果重新推理"
```

#### 场景 2: 多次编辑同一消息的版本链管理

```
数据结构:
messages 表增加 version 字段:
  id: "msg-001"
  version: 1 (当前)
  
message_versions 表 (新表):
  id: "ver-001"
  message_id: "msg-001"
  version: 1
  content: "原始内容"
  edited_at: 1700000000
  
  id: "ver-002" 
  message_id: "msg-001"
  version: 2
  content: "第一次修改"
  edited_at: 1700000100

UI: 消息旁显示 "v3" 标记，点击可展开版本列表
    每个版本可预览 / 恢复为此版本 / 从此版本继续
```

#### 场景 3: 回退后原路径的保留策略

```
问题: 用户回退到 step 5 重新执行，step 6-10 的原执行路径如何保留?

保留策略:
1. step 6-10 的消息标记为 is_stale = true (不删除)
2. 新的执行从 step 5 开始，新消息 seq 从 6 继续
3. 原 step 6-10 在 UI 中折叠显示为 "已废弃路径"
4. 用户可点击展开查看原始路径内容
5. 用户可"恢复此路径": 撤销回退，回到原 step 10
6. 存储成本: 废弃路径保留 30 天，之后可自动清理 (可配置)

数据模型:
messages 表:
  - is_stale: BOOLEAN (是否在废弃路径上)
  - stale_parent_id: TEXT (废弃原因: 指向触发回退的消息 ID)
```

#### 场景 4: 分支探索的会话管理

```
问题: 用户频繁 fork 会产生大量分支会话，如何管理?

1. 分支会话自动命名: "任务名 - 分支 #N"
2. 分支树面板: 显示主会话和所有分支的树形关系
3. 分支会话默认不归档，手动标记完成后归档
4. 分支合并: 如果某个分支的结果更好，可将该分支"设为主路径"
   - 主路径标记: is_main_path = true
5. 存储优化: 分支会话共享 fork 点之前的消息 (通过 fork_from 引用)
```

**MCP Server 配置**:

```typescript
interface MCPServerConfig {
  id: string;
  name: string;
  transport: 'stdio' | 'sse' | 'http';
  // stdio 模式
  command?: string;
  args?: string[];
  env?: Record<string, string>;
  // HTTP/SSE 模式
  url?: string;
  headers?: Record<string, string>;

  timeout: number;                // 秒
```

**MCP 生命周期**:

```
1. 启动: 根据 transport 启动对应连接
   - stdio: spawn 子进程
   - SSE: 建立 SSE 连接
   - HTTP: 建立 HTTP 客户端

2. 初始化:
   2.1 发送 initialize 请求
   2.2 获取 ServerCapabilities (tools/resources/prompts)
   2.3 发送 initialized 通知

3. 工具发现:
   3.1 调用 tools/list 获取工具列表
   3.2 将工具注册到 ToolRegistry (source=mcp, server_id=xxx)

4. 运行时:
   4.1 工具调用: 通过 tools/call 转发
   4.2 资源读取: 通过 resources/read 转发
   4.3 健康检查: 定期 ping

5. 关闭:
   5.1 stdio: kill 子进程
   5.2 SSE/HTTP: 断开连接
   5.3 从 ToolRegistry 注销工具
```

#### 2.4.2 Hooks 系统

```
功能编号: F-EXT-002
功能名称: Hooks 系统
优先级: P0 (核心亮点)
```

**Hook 定义**:

```typescript
interface HookConfig {
  id: string;
  name: string;
  trigger: HookTrigger;
  script: string;        // 脚本路径或内联代码
  language: 'typescript' | 'python' | 'shell';
  enabled: boolean;
  timeout: number;       // 秒
  on_error: 'skip' | 'warn' | 'abort';
  can_intercept: boolean; // pre_* hooks 可拦截
}
```

**Hook 触发点与参数**:

| Hook 点 | 参数 | 返回值 | 可拦截 |
|----------|------|--------|:---:|
| `on_session_start` | session_id, project_path | void | ❌ |
| `on_session_end` | session_id, summary | void | ❌ |
| `pre_plan` | task_description, context | modified_task? | ✅ |
| `post_plan` | plan: TaskPlan | modified_plan? | ✅ |
| `pre_act` | tool_name, args, context | modified_args? | ✅ |
| `post_observe` | observation: Observation | modified_observation? | ✅ |
| `on_tool_call` | tool_name, args, session_id | void | ❌ |
| `on_tool_result` | tool_name, result, duration | void | ❌ |
| `on_file_change` | file_path, change_type | void | ❌ |
| `on_test_fail` | test_results, session_id | void | ❌ |
| `on_task_complete` | task_id, result, summary | void | ❌ |
| `pre_model_call` | messages, config | modified_messages? | ✅ |
| `post_model_call` | response, token_usage | modified_response? | ✅ |
| `on_cost_warning` | current_cost, budget_limit | void | ❌ |

**Hook 执行流程**:

```
1. 触发点到达
2. 查询匹配的 Hook 配置 (从数据库)
3. 对每个匹配的 Hook:
   3.1 构造 Hook 输入 (JSON)
   3.2 在沙箱中执行脚本
   3.3 等待执行完成或超时
   3.4 解析返回值
   3.5 如果是拦截型 Hook:
       - 返回值包含 modified_* 字段 → 使用修改后的值
       - 返回值包含 abort: true → 中断操作
       - 无返回值 → 继续原操作
4. 如果多个 Hook 同时触发: 按配置顺序串行执行
```

**Hook 沙箱**:

- 文件系统: 限制在项目根 + 配置的 allowlist
- 网络: 默认禁止，需显式声明
- 环境变量: 继承 Agent 进程环境 (脱敏)
- 超时: 每个 Hook 默认 30s
- 资源限制: 内存上限 256MB

```
   - ...

3. 用户确认导入策略:
   - 冲突处理: skip | overwrite | rename
   - 导入范围: 全选或勾选

4. 执行导入:
   - 解压到临时目录
   - 合并数据库 (ATTACH + INSERT OR REPLACE/IGNORE)
   - 复制附件文件
   - 验证数据完整性

5. 导入完成，通知用户
```

### 2.7 对话交互系统

#### 2.7.1 流式对话

```
功能编号: F-CHAT-001
功能名称: 流式对话渲染
优先级: P0
```

**消息结构**:

```typescript
interface Message {
  id: string;
  session_id: string;
  seq: number;
  role: 'user' | 'assistant' | 'tool' | 'system';
  content: MessageContent;
  original_content?: MessageContent;
  edited_at?: number;
  is_stale: boolean;
}

interface MessageContent {
  parts: ContentPart[];
}

type ContentPart =
  | { type: 'text'; text: string }
  | { type: 'tool_call'; tool_id: string; tool_name: string; args: any }
  | { type: 'tool_result'; tool_id: string; result: any; is_error: boolean }
  | { type: 'image'; base64: string; mime_type: string }
  | { type: 'file_ref'; file_path: string; range?: [number, number] }
  | { type: 'diff'; hunks: DiffHunk[] }
  | { type: 'thinking'; text: string };  // 模型思考过程
```

**流式渲染流程**:

```
1. 用户发送消息 → 创建 user Message → 持久化
2. 创建空的 assistant Message (seq = user.seq + 1)
3. 启动 LLM 流式调用:
   - text_chunk → 追加到 Message.content.parts (流式渲染)
   - tool_call → 追加 tool_call part → 创建 tool Message
   - tool_result → 追加 tool_result part → 更新 tool Message
   - done → 标记 Message 完成 → 持久化
4. 如果用户点击停止:
   - 取消 LLM 请求
   - 标记 Message 为 interrupted
   - 保留已生成内容
```

| 能力位检测 | provider_id | capability_mask | healthCheck 通过 | 缺失能力走 polyfill |
| 模型路由 | taskKind + capabilityRequired + budgetWeight | 选定 Provider | 至少 1 个活跃 Provider | 计费跟进 |
| Fallback 降级 | 主 Provider 健康检查失败 | 沿 fallback_chain 降级;Ollama 兜底 | fallback_chain 定义 | 重试或切换记录 audit |
| 自定义 Adapter 注册 (v0.3) | npm 包含 class extends baseAdapter | registry 项 | Plugin 加载完成 | 与内置 Provider 同等待遇 |
| 计费 | usage + model_token pricing | model_calls 写入 | Pricing 表存在 | cost 归因 |
| Anthropic system-as-role 适配 | provider_kind='anthropic' | message 转换 | - | 主 Loop 统一发送 |
| OpenAI 兼容端点 | config.baseURL + key | 通用 OpenAI 兼容 Adapter | 端点可达 | 同 chat/chatStream 接口 |

#### 2.14.2 Adapter 契约 (v4.3 06 §3.17.2)

`AIProviderAdapter { id, kind, capabilities, models, chat(), chatStream(), embed?(), countTokens(), estimateCost(), healthCheck() }`

#### 2.14.3 数据流

`ProviderRouter.route(taskKind, capabilityRequired, budgetWeight)` → 选定 Adapter → Adapter.chatStream → 异步 ChatChunk 流回流主 Loop Act 阶段 → 计费写入 `model_calls` → 重试/降级经 `FallbackChain` 处理。

## 5. 数据流规格

### 5.1 主数据流

v2.1 起，所有客户端与后端的通信统一经 JSON-RPC 2.0 Transport 层，不再使用进程内直接函数调用或仅 Electron IPC。客户端发起请求，经 Transport 编码为 JSON-RPC 消息送达 @openwork/server，由 Server 路由至 @openwork/core 引擎执行；引擎产生的事件流经反向 Transport 通道推送回客户端实时渲染。下图为分层主数据流:

```
┌─────────────────────────────────────────────────────────────────┐
│  客户端层 (Desktop / TUI / Web / CLI / 自定义)                    │
│    用户输入 → 构造 JSON-RPC 请求              ▲   事件流渲染       │
└──────────────────┬──────────────────────────┼───────────────────┘
                   │ JSON-RPC 2.0 请求        │ JSON-RPC 2.0 事件/响应
                   ▼                          │
┌─────────────────────────────────────────────────────────────────┐
│  Transport 层 (HTTP/SSE · WebSocket · stdio · EIPC · Embedded)   │
│    编解码 · 连接管理 · 鉴权 · 重连                                │
└──────────────────┬──────────────────────────┼───────────────────┘
                   │                          │
                   ▼                          │
┌─────────────────────────────────────────────────────────────────┐
│  @openwork/server (后端 Server)                                  │
│    方法路由 (session/message/tool/...) · 事件订阅转发             │
└──────────────────┬──────────────────────────┼───────────────────┘
                   │                          │
                   ▼                          │
┌─────────────────────────────────────────────────────────────────┐
│  @openwork/core (Agent 核心引擎)                                 │
│                                                                  │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐                  │
│   │ Context  │───►│ Prompt   │───►│  Model   │                  │
│   │ Engine   │    │ Engine   │    │ Provider │                  │
│   └──────────┘    └──────────┘    └────┬─────┘                  │
│                                      │                           │
│              ┌──────────┐             ▼                          │
│              │ Session  │        ┌─────────┐                     │
│              │ Store    │◄───────│  Tool   │                     │
│              └────┬─────┘        │Dispatcher│                    │
│                   │              └─────────┘                     │
│                   ▼                                              │
│              ┌──────────────┐  事件回流                          │
│              │  Event Bus   │──────► Server ──► Transport ──► 客户端
│              └──────┬───────┘                                    │
│                     │                                            │
│        ┌────────────┼────────────┐                               │
│        ▼            ▼            ▼                               │
│   ┌─────────┐ ┌──────────┐ ┌────────────┐                       │
│   │  Audit  │ │Persistence│ │  事件推送   │                       │
│   │ Logger  │ │ (SQLite)  │ │            │                       │
│   └─────────┘ └──────────┘ └────────────┘                       │
└──────────────────────────────────────────────────────────────────┘
```

**关键说明**:
- 客户端仅持有 UI 状态与渲染逻辑，不直接访问数据库或 @openwork/core 内部 API。
- 同一后端 Server 可同时承载多个客户端连接 (Desktop 本地、Web 远程、CLI 脚本等)，会话/配置/记忆互通。
- Embedded Transport 模式下客户端与 Server 同进程，跳过网络栈但仍走 JSON-RPC 编解码，保持契约一致性。

## 6. 错误处理规格

### 6.1 错误分类

| 错误类型 | 严重级别 | 处理策略 | 用户提示 |
|----------|:---:|----------|----------|
| LLM API 错误 (网络/限流/认证) | 中 | Fallback + 重试 | "模型调用失败，正在切换到备选模型..." |
| LLM API 错误 (内容过滤) | 中 | 通知用户 + 不重试 | "内容被模型安全策略拒绝，请修改输入" |
| 工具执行超时 | 低 | 返回 timeout 给 LLM | 工具调用卡片显示超时标记 |
| 工具执行异常 | 低 | 返回 error 给 LLM | 工具调用卡片显示错误详情 |
| 沙箱违规 | 高 | 阻止 + 审计 | "操作被安全策略阻止: [原因]" |
| 数据库错误 | 高 | 重试 3 次 + 通知 | "数据存储异常，请检查磁盘空间" |
| 配置校验失败 | 低 | 拒绝变更 + 提示 | "配置无效: [具体字段] [错误原因]" |
| 导入格式错误 | 低 | 拒绝导入 + 提示 | "导入文件格式不正确: [原因]" |
| 内存不足 | 高 | 尝试释放 + 通知 | "内存不足，正在优化..." |
| 崩溃 | 极高 | 自动恢复 | 重启后提示 "检测到上次异常退出，已恢复未完成会话" |

### 6.2 错误恢复策略

```
错误发生
  │
  ├── 可恢复错误 (API/超时/网络)
  │   ├── 第 1 次: 立即重试
  │   ├── 第 2 次: 指数退避 (1s)
  │   ├── 第 3 次: 指数退避 (4s)
  │   └── 仍失败: Fallback / 通知用户
  │
  ├── 工具错误 (非致命)
  │   └── 返回结构化错误给 LLM，让其自行恢复
  │
  └── 不可恢复错误 (崩溃/致命)
      └── 保存检查点 → 优雅关闭 → 下次启动恢复
```
